Part 0

Where we start

Same laptop, same environment as analyst session 1, same mocked bucket name, acme-lake. The difference tonight is one decorator. By default moto lets every call through, which is fine for building a lake and useless for testing who may use it. moto can also check calls against the IAM policies attached to the caller, and that is the switch we flip. IAM is how AWS decides whether a request is allowed: every call to every service is checked against the policies that apply to whoever made it. Reading those policies fluently is the single most useful AWS skill an analyst can own, because "AccessDenied" is the error you will see most.

Part 1 · covers the elements of a policy

A policy is a list of statements

5 min live

An IAM policy is a JSON document with a Version and a list of Statements. Each statement says one thing: this Effect (Allow or Deny) applies to these Actions on these Resources, optionally only when a Condition holds. Everything a statement does not match is simply not mentioned, and in IAM "not mentioned" means no. The IAM User Guide puts it in one line: "By default, all requests are implicitly denied with the exception of the AWS account root user, which has full access."

LiveThe analyst policy, line by line3 min▶

Version. "2012-10-17" is the date of the policy language, not of your policy. Write it every time and never change it.

Statement and Sid. The policy holds two statements. A Sid is a name for humans, logs and code review; it matches nothing. Name each statement for the job it does, ReadCurated and KeepTheLake, and a reviewer can read the intent before the detail.

Effect, Action, Resource. ReadCurated allows two actions, s3:GetObject (read an object) and s3:ListBucket (list keys), on two ARNs. The two ARNs are not redundant. arn:aws:s3:::acme-lake is the bucket, and listing is an action on the bucket. arn:aws:s3:::acme-lake/curated/* is every object whose key starts with curated/, and reading is an action on an object. Grant ListBucket only on bucket/* and listing fails; grant GetObject only on the bucket ARN and every read fails. The prefix from session 1 is doing real work here: the slash in the key is what lets a policy draw a line between zones.

The second statement. KeepTheLake denies deleting the bucket and replacing its bucket policy, on every resource. It exists so that no Allow added later, by anyone, can grant those two actions to this user. Part 2 is about why that works.

Self-studyHow Action and Resource are matched3 min▶

Actions. The IAM User Guide, "Policy elements: Action": "The prefix and the action name are case insensitive", so s3:getobject matches s3:GetObject. Wildcards work: * for any run of characters and ? for one, as in the guide's example iam:*AccessKey*, which covers creating, listing, updating and deleting access keys in one pattern.

Resources. "Policy elements: Resource": wildcards can sit inside ARN segments. The guide's example pattern bucket/*/test/* matches bucket/1/2/test/3/object.jpg and does not match bucket/1-test/object.jpg, because the slash is part of the pattern. Case is not forgiven the way it is for actions: "In the Resource element, the IAM user name is case sensitive." Treat every ARN as exact text and copy it rather than retyping it.

NotAction, the inverted list. NotAction with Allow grants everything except what you list; the guide's example "allows users to access every action in every AWS service except for IAM", and warns that it "could result in granting users more permissions than you intended." If you meet one in review, read it as a wildcard and ask what it lets through.

Real world

The policy that could read every file and list none. An analyst is granted s3:ListBucket and s3:GetObject on arn:aws:s3:::lake/curated/* only. Reading a known key works; every attempt to list a folder fails with AccessDenied, and the team spends an afternoon blaming the console. Listing is an action on the bucket ARN, which the policy never mentions. The fix is the two-ARN shape in the script above. The scenario is constructed; the matching rule is the one in the IAM User Guide.

Part 2 · covers explicit deny and conditions

Guardrails and conditions

6 min live

An Allow opens a door; it never locks one. Locking takes a Deny, and the IAM User Guide's evaluation rule makes it final: "An explicit deny overrides an explicit allow." That is why KeepTheLake is written as a separate Deny statement rather than left to the absence of an Allow. A Condition narrows either effect to requests whose context matches: sent over HTTPS, from an address range, by a principal with a given tag. Conditions have their own logic, and it is short enough to learn as wiring.

LiveExplicit deny: the guardrail no Allow can undo3 min▶

The IAM User Guide, "Policy evaluation logic", gives three outcomes and a strict order between them. A request starts denied. An Allow that matches lifts that default. A Deny that matches, in any policy that applies, ends the evaluation: "An explicit deny overrides an explicit allow." So there are two kinds of no. An implicit deny means nothing allowed the request, and the next Allow someone attaches will change the answer. An explicit deny means a statement forbade it, and no Allow anywhere changes the answer.

That is the whole design of KeepTheLake. Today the analyst user has no Allow for s3:DeleteBucket, so an implicit deny would already stop it. The explicit Deny is for next quarter, when someone attaches a broad managed policy to the same user to fix an unrelated ticket. The guardrail holds anyway. The analyst session 8 bench measures this: adding "Action": "*", "Resource": "*" to the analyst role takes it from 7 to 22 of 24 data-team actions allowed, and the two explicit Denies, DeleteBucket and PutBucketPolicy, are the two that still hold.

Self-studyThe operators you will meet first4 min▶

From the IAM User Guide, "Condition operators" and "Conditions with multiple context keys or values":

Bool. The classic use is refusing plain HTTP. A Deny with "Bool": {"aws:SecureTransport": "false"} fires on any request sent without TLS. Read the missing-key rule into it: if a request carries no aws:SecureTransport key at all, "the values do not match and the condition is false", so this Deny does not fire on that request. The analyst session 8 bench has that exact case, T22.

★ A Deny that refuses plain HTTP to the lake{ "Sid": "HttpsOnly", "Effect": "Deny", "Action": "s3:*", "Resource": ["arn:aws:s3:::acme-lake", "arn:aws:s3:::acme-lake/*"], "Condition": { "Bool": { "aws:SecureTransport": "false" } } }

IpAddress. Matches the caller's address against CIDR ranges in aws:SourceIp. A value written without a prefix length is treated as /32, a single address.

StringEquals. "Exact matching, case sensitive". growth and Growth are different teams to IAM. Gating on principal tags is attribute-based access control; the concept, and when to choose it over roles, belongs to learn-data-access-control. Here we only read the JSON.

Combining. Several operators in one Condition are ANDed, several keys are ANDed, several values for one key are ORed, and for negated operators several values combine as NOR: the request must match none of them.

Real world

The office-only rule that locked out the pipeline. A team adds a Deny on S3 with NotIpAddress listing the office ranges, meaning "refuse anyone outside the office". It works for people. Then a scheduled job, running somewhere with an address that is not on the list, starts failing with AccessDenied every night. The negated operator did exactly what it says: any address not on the list, or no address key at all, makes the Deny fire. The scenario is constructed; the operator behaviour is the one in "Condition operators". Before you ship a negated Deny, list every caller that will be evaluated against it.

Part 3 · covers moto's IAM enforcement and its limits

A mock that says no, but not why

4 min live

moto can enforce IAM on calls made with credentials it issued. The switch is a decorator, @set_initial_no_auth_action_count(8): the first 8 calls run unchecked, as an administrator would, so the script can build the bucket, the user and the policy; every call after that is checked against the caller's attached policies. That is enough to watch a policy work. It is not AWS's engine, and the difference is worth knowing before you trust a green test.

LiveWhat the mock proves, and what it does not2 min▶

What it proves. The calls are real boto3 calls with real request shapes, signed with ana's access key, and moto answers ALLOWED or AccessDenied from the policy you wrote. Change one ARN and the answer changes. That is a genuine feedback loop for policy-as-code, and it costs nothing.

What it does not. moto's enforcement is a teaching aid, not AWS's engine. It returns the same AccessDenied for an implicit deny and an explicit one, so it never tells you which step denied. It does not model your organization's SCPs or RCPs. And a mock accepts things AWS would refuse: in analyst session 5 moto accepts a 901-second Lambda timeout that real Lambda rejects, because a mock is not a quota check. For the step-by-step answer, the analyst session 8 bench, The IAM and cost bench, follows the order in AWS's "Policy evaluation logic" and is tested against 36 cases, each tied to a sentence in the docs, 36 of 36 passing.

The counter is a setting you own. The 8 has to cover every setup request the script makes before ana's first call. Set it too low and setup fails with AccessDenied; set it too high and ana's first test call runs unchecked and reports ALLOWED for the wrong reason. The AccessDenied lines in the real output are the evidence that enforcement was on by then; if you add a setup step, raise the number with it.

Self-studyWhy the access key in the script is a smell2 min▶

The script calls create_access_key because moto needs credentials it issued in order to know who is calling. That is the only reason. In a real account, an access key is a long-term secret that works until someone deletes it, from anywhere it is pasted. AWS's "Security best practices in IAM" is direct: "Where possible, we recommend relying on temporary credentials instead of creating long-term credentials such as access keys." For people: "Require your human users to use temporary credentials when accessing AWS." For code: "Require workloads to use temporary credentials with IAM roles to access AWS".

So in production the same JSON is attached to a role, and a person or a job assumes the role and receives credentials that expire. The policy text does not change at all, which is the point of keeping it as code. The same page recommends IAM Access Analyzer, which "analyzes the services and actions that your IAM roles use, and then generates a fine-grained policy that you can use", and phishing-resistant MFA "such as passkeys and security keys" where a user must exist. Least privilege as a principle, and how to run access reviews, belongs to learn-data-access-control.

Real world

The key in the notebook. An analyst pastes an access key into the first cell of a notebook "just to test", and the notebook is pushed to a shared repository with its outputs. The key still works months later because nothing expires it. Rotating it breaks two scheduled jobs nobody knew depended on it. The scenario is constructed; the remedy is AWS's own best practice above: roles and temporary credentials, so there is no long-lived secret to paste.

Build-along

Four calls against an enforced policy

★ 22 min · everyone builds

One Python file, about forty lines, a few seconds to run. It builds the lake as an administrator, creates the user ana with the analyst policy attached, then makes four calls as ana. The output below is pasted from a real run of exactly this code. Predict each line before you run it.

Reuse the environment from analyst session 1. Same folder, same .venv, same pinned versions; nothing new to install. If you are starting fresh, run analyst session 1's step 1 first. This script needs no data file.

★ Step 1 · setup (verified 3 October 2026). .venv/bin/activate python -c "import moto, boto3; print(moto.__version__, boto3.__version__)" # expect 5.2.3 1.43.108

Write the policy as a Python dict. This is the JSON from Part 1, character for character. Keeping it in code means it is reviewed in a pull request and rerun on every change, like any other code.

★ Step 2 · b2_policies.py, part 1# Analyst session 2 - IAM policies as code, enforced by moto against a real boto3 call import json, os, boto3 from moto import mock_aws from moto.core import set_initial_no_auth_action_count os.environ.setdefault("AWS_DEFAULT_REGION", "us-east-1") ANALYST_POLICY = { "Version": "2012-10-17", "Statement": [ {"Sid": "ReadCurated", "Effect": "Allow", "Action": ["s3:GetObject", "s3:ListBucket"], "Resource": ["arn:aws:s3:::acme-lake", "arn:aws:s3:::acme-lake/curated/*"]}, {"Sid": "KeepTheLake", "Effect": "Deny", "Action": ["s3:DeleteBucket", "s3:PutBucketPolicy"], "Resource": "*"}, ], }

Build the lake and the user as an administrator. These are the unchecked setup calls the counter allows: one bucket, a curated and a raw object, the user ana, the managed policy, the attachment, and the access key moto needs to identify ana. The last line builds an S3 client that signs every request as ana.

★ Step 3 · b2_policies.py, part 2@set_initial_no_auth_action_count(8) # the first 8 calls (setup) run as admin; then IAM is enforced @mock_aws def main(): iam, admin_s3 = boto3.client("iam"), boto3.client("s3") admin_s3.create_bucket(Bucket="acme-lake") admin_s3.put_object(Bucket="acme-lake", Key="curated/nyc_taxi/part-0.parquet", Body=b"PAR1...") admin_s3.put_object(Bucket="acme-lake", Key="raw/nyc_taxi/trips.csv", Body=b"VendorID,...") iam.create_user(UserName="ana") arn = iam.create_policy(PolicyName="analyst-lake-read", PolicyDocument=json.dumps(ANALYST_POLICY))["Policy"]["Arn"] iam.attach_user_policy(UserName="ana", PolicyArn=arn) key = iam.create_access_key(UserName="ana")["AccessKey"] ana = boto3.client("s3", aws_access_key_id=key["AccessKeyId"], aws_secret_access_key=key["SecretAccessKey"])

Make four calls as ana and print what comes back. Each call either succeeds or raises a ClientError; the error code is read from the response, exactly as you would in production code.

★ Step 4 · b2_policies.py, part 3 tries = [ ("GetObject curated", lambda: ana.get_object(Bucket="acme-lake", Key="curated/nyc_taxi/part-0.parquet")), ("GetObject raw", lambda: ana.get_object(Bucket="acme-lake", Key="raw/nyc_taxi/trips.csv")), ("PutObject curated", lambda: ana.put_object(Bucket="acme-lake", Key="curated/x.parquet", Body=b"x")), ("DeleteBucket", lambda: ana.delete_bucket(Bucket="acme-lake")), ] for name, call in tries: try: call(); print(f"{name:18s} ALLOWED") except Exception as e: print(f"{name:18s} {e.response['Error']['Code']}") main()

Run it and compare with this real output. Then read each line against the grid above. Line 1: ReadCurated matches both the action and the curated/* ARN. Line 2: the action matches but no Allow names a raw/ ARN, so the default deny stands. Line 3: the ARN matches but s3:PutObject is not in the Action list, the same implicit deny for a different missing piece. Line 4: KeepTheLake matches, an explicit deny, final whatever else is attached. Notice that lines 2 to 4 print the same word; the reason lives in the policy, not in the error.

Check yourself

Three questions

Clear all three and analyst session 2 gets stamped in your passport.

1 · Why does the analyst policy list both arn:aws:s3:::acme-lake and arn:aws:s3:::acme-lake/curated/*?

Listing is an action on the bucket ARN; reading is an action on an object ARN. Grant either one against the wrong ARN and it never matches.

2 · Reading raw/nyc_taxi/trips.csv came back AccessDenied. Which statement denied it?

KeepTheLake only covers DeleteBucket and PutBucketPolicy. Every request starts denied, and nothing lifted that default for raw/. An Allow attached later could change this answer; an explicit Deny could not be undone.

3 · The script calls create_access_key. Why is that a smell in a real account?

"Security best practices in IAM" recommends relying on temporary credentials instead of long-term keys. The same policy JSON attaches to a role unchanged.
