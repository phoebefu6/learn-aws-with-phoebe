Compute or serverless

Every engine on AWS runs on a meter. Some meters tick only while a query reads bytes, some only while your code is running, and some tick every hour of every day whether or not work arrives. Tonight we read those meters the way a data leader needs to: what each one counts, where Lambda's hard walls sit, and the point at which a function that costs a cent a month becomes dearer than a small container left on all the time.

Part 1 · covers the meter each engine runs on

Four meters, one day

5 min live

Four engines carry most of a data team's work on AWS, and each one bills by a different unit. Athena bills the bytes a query reads. Lambda bills the time your code runs, multiplied by the memory you gave it. Fargate bills a container's vCPU and memory for every hour it exists. Redshift Serverless bills warehouse capacity per second while queries run, and nothing for compute when they do not. Put all four against the same day and the difference stops being abstract.

LiveFour meters, four units2 min▶

Athena: bytes. $5.00 per TB scanned. Session 2 showed why layout matters, and session 5 turns it into a monthly bill: a query on a badly laid out table reads everything, every time.

Lambda: time times memory, plus requests. $0.0000166667 per GB-second for the first tier, plus $0.20 per million requests. The pricing page is precise about the clock: duration "is calculated from the time your code begins executing until it returns or otherwise terminates, rounded up to the nearest 1ms".

Fargate: hours of existence. $0.04048 per vCPU-hour and $0.004445 per GB-hour. A container that is running is billing, whether it is transforming a file or waiting for one.

Redshift Serverless: capacity while queries run. $0.375 per RPU-hour, where one RPU "provides 16 GB of memory". The billing page says "When no queries are running, you aren't billed for compute capacity." All four prices are us-east-1, AWS Price List, 3 October 2026, and must be re-verified before you rely on them.

LiveThe minimums that shape small jobs2 min▶

Every meter has a smallest unit, and for small, frequent work the smallest unit is the bill. Athena charges "for the number of bytes scanned per query, rounded up to the nearest megabyte, with a 10 MB minimum per query." On the 100,000-row taxi sample used by the analyst track, every query is smaller than that, so every query bills the minimum: $0.000048 (us-east-1, AWS Price List, 3 October 2026).

Redshift Serverless bills "in RPU-hours on a per-second basis, with a 60-second minimum charge." Analyst session 6 models what that means: a 5-second query on an idle 8 RPU warehouse bills $0.0500, not the $0.0042 its five seconds would suggest (modelled; same Price List, re-verify before relying on it). Lambda's unit is 1 ms, so it has the least rounding of the four. Fargate has none of these problems and one bigger one: it never stops on its own.

Self-studyStorage and the small print2 min▶

Storage is its own meter and runs all month. Redshift's billing page: "Storage is billed by GB / month. Storage billing is separate from billing for compute capacity." Managed storage is $0.024 per GB-month (us-east-1, AWS Price List, 3 October 2026; re-verify). The lake itself bills S3 storage, which session 2 priced.

Two sentences from the same page belong in any review of a warehouse bill. "Maintaining open connection pools can generate costs even when no actual user workloads are running." And "If you run a query and cancel it before it finishes, you are still billed for the time the query ran." Athena has a matching rule: no charge for DDL or failed queries, but cancelled queries are billed for the data they scanned. "Idle is free" is true only when the engine can see that it is idle.

EC2, AWS's virtual machines, is a fifth meter (instance hours) and the base under many managed services; instance families, networking, Savings Plans and Reserved Instances are not taught on these pages.

Real world

The container that waited all day. A team needs one partner file a day turned into Parquet. The engineer who builds it knows containers, so it ships as a small Fargate service, 1 vCPU and 2 GB, that polls the bucket every minute. It works for a year. At the annual cost review someone notices it has been billing every hour of every day to do about twenty seconds of work: $36.04 a month for a job that, run as a Lambda function on the same file, models at $0.01 (modelled; us-east-1, AWS Price List, 3 October 2026; re-verify). The money is small. The habit is not: every always-on service in the estate deserves the question "how much of the day is it working?" Constructed, from a common pattern.

Part 2 · covers Lambda's limits as a design constraint

The limit box

6 min live

Lambda is cheap for short work because AWS runs it inside fixed walls. A job either fits inside those walls or it does not, and no amount of tuning moves a wall. The leader's question is not "is serverless good?" but "does this job fit the box today, and will it still fit when the data doubles?" All the walls below come from AWS's "Lambda quotas" page, read on 3 October 2026; quotas change, so re-read it before a design review.

LiveThe 900-second wall2 min▶

The quota reads "900 seconds (15 minutes)." When a run reaches it, Lambda stops the run. It is not a soft target and it cannot be raised. That makes duration the first thing to ask about any job proposed for Lambda, and the second thing is its trend: a job that takes 9 minutes on this year's volume is a job that will take longer on next year's.

Jobs past the wall have three honest options: split the work into pieces that each fit (one file per run instead of one night per run), move it to a container that can run as long as it needs, or move the heavy part into a query engine that is built for it. Which one is right depends on the pipeline design, and that design is taught in learn data engineering.

LiveMemory buys CPU2 min▶

Lambda memory runs from "128 MB to 10,240 MB, in 1-MB increments", and CPU comes with it: "At 1,769 MB, a function has the equivalent of one vCPU." A function given 512 MB to save money gets a fraction of a CPU, runs longer, and may cost the same or more, because the meter is memory times time. Scratch disk is separate: /tmp is configurable "Between 512 MB and 10,240 MB".

The leader's version: a job that needs more than 10,240 MB of memory, such as a scoring model that loads 14 GB, does not fit however short it is. That is a container's or a dedicated service's job, and GPU or inference infrastructure belongs to learn AI infra.

Self-studyPayloads, packages, concurrency and the free tier2 min▶

Payloads. "6 MB each for request and response (synchronous)", "1 MB (asynchronous)", and "200 MB for each streamed response". The asynchronous figure is 1 MB; older articles and diagrams still say 256 KB, which is out of date. Either way the norm holds: pass a pointer to the data (an S3 key), never the data itself.

Packages. 50 MB zipped and 250 MB unzipped for a zip deployment including layers, or a container image of up to 10 GB. Heavy libraries are the usual reason a team moves to the image route.

Concurrency. 1,000 concurrent executions by default, raisable, with a caveat worth checking on a fresh account: "New AWS accounts have reduced concurrency and memory quotas". A backfill of 10,000 files that all land at once queues against that ceiling.

Free tier. "The free tier includes one million requests and 400,000 GB-seconds per month." One more caution from the analyst track: in analyst session 5 a local mock, moto, accepted a 901-second timeout that real Lambda rejects. A mock is not a quota check; the quotas page is.

Real world

The nightly job that grew past 15 minutes. A nightly reconciliation was written as one Lambda function in its first month, when it took four minutes. Volume grew, nobody watched the duration, and one night it hit 900 seconds and stopped halfway. The morning dashboard showed yesterday's numbers as today's, and the first person to notice was a regional manager. The fix was not more memory; it was splitting the run into one invocation per region, each well inside the wall, plus an alarm on duration at 600 seconds. Constructed, from a common pattern.

Part 3 · covers the crossover between a function and a container

Where the lines cross

4 min live

Analyst session 5 takes one real workload shape, a 20-second run at 1 GB of memory, and prices it on two engines with real us-east-1 prices from the AWS Price List on 3 October 2026. The workloads are modelled; the prices are not. Lambda's cost rises with every run. A Fargate container sized at 1 vCPU and 2 GB costs the same every month whether it runs once or all the time. Somewhere the two lines cross.

LiveThree numbers, one crossover2 min▶

The same 20-second, 1 GB run. Once a day on Lambda: $0.01 a month. Once a minute: $14.41. A Fargate container at 1 vCPU and 2 GB, always on: $36.04. Each Lambda run costs $0.000333534: twenty seconds at $0.0000166667 per GB-second plus its share of $0.20 per million requests. Divide the container's month by that and the lines cross at about 108,000 invocations a month. All figures: us-east-1, AWS Price List, 3 October 2026, modelled workloads, before any free tier; re-verify prices before relying on them.

The surprise for most rooms is how far apart the ends are. One file a minute, all month, is still well under half the cost of the container. A function that runs often is not automatically expensive; a container that runs rarely is.

LiveThe rule of thumb, and where it bends1 min▶

Spiky and short: functions. Work that arrives in bursts and finishes well inside 900 seconds fits Lambda's meter, which stops between bursts. Steady and long: containers. Work that runs most of the day, or runs past the wall, fits a container, whose meter is running anyway. Questions asked in SQL: a per-byte engine or a warehouse. That is not a compute choice at all; it is Athena's bytes against Redshift Serverless's RPU-seconds, and analyst session 6 models where they break even: about 31 queries a day against one busy warehouse hour, about 123 against four (modelled; 20 GB scanned per query, 8 RPU; your numbers will differ).

The rule bends at the edges. A job close to the crossover should be decided on the trend, not today's count. Continuous event streams, where work never stops arriving, are their own design problem and belong to learn streaming data.

Self-studyWhat the model leaves out2 min▶

The comparison is honest about its scope, and yours should be too. It applies no free tier: on a quiet account Lambda's first one million requests and 400,000 GB-seconds a month are free, which moves the cheap end lower still. It prices Fargate always on; a container started only when needed and stopped after is a different, cheaper shape, and how a short task's time is rounded should be read on the Fargate pricing page before you model it. It ignores the people cost, which often decides: a team that already runs containers well may rationally pay the difference. And it uses one Region's list prices, which change without notice.

Savings Plans and Reserved Instances change the container side of the comparison and are not taught on these pages. The method transfers even when the prices move: price one run, price one always-on month, divide, and compare against how often the job really runs.

Real world

One a day became one a minute. A product team moves a partner feed from a daily drop to a file every minute. The data lead's first instinct is to migrate the Lambda ingest to a container "before it gets expensive". Someone prices it first: the same function at one a minute models at $14.41 a month, against $36.04 for the container always on (modelled; us-east-1, AWS Price List, 3 October 2026; re-verify). The function stays, with a note that the question comes back if the feed passes about 108,000 files a month or a run approaches 900 seconds. Constructed; the numbers come from analyst session 5.

Build-along

Five jobs, five meters

★ 22 min · everyone builds

No console and no account. Take five jobs your team runs or is about to build, and describe each one by four facts before anyone names a service: how long one run takes, how often it runs, how much memory it needs, and which meter that shape belongs on. The engine falls out of the meter, not the other way round. The worked examples below are constructed; your jobs and your numbers will differ.

List five jobs. Mix them on purpose: one that reacts to a file landing, one nightly batch, one service that answers requests all day, one analyst's ad hoc SQL, and one dashboard that refreshes on a timer. If your team runs fewer kinds, pick five real ones anyway; the sheet is about your estate, not the textbook mix.

Write the four facts for each. How long one run takes today, and its trend. How often it runs. How much memory it needs at peak. Whether its work is code running or a SQL question reading data. Leave the engine column empty until all four are written.

★ Worked example: five jobs, four facts (constructed)1 File lands, convert to Parquet 20 s about once a day 1 GB 2 Nightly reconciliation 22 min once a night 3 GB 3 Scoring service for the app always on steady all day 4 GB 4 Analyst ad hoc SQL on the lake seconds about 20 a day n/a, SQL 5 Executive dashboard refresh seconds every 5 minutes n/a, SQL

Pick the meter, then the engine. Ask which meter would stop when the job stops. Then check the walls from Part 2: duration under 900 seconds, memory under 10,240 MB, payloads passed as S3 keys.

★ Worked example: meter and engine (constructed)1 GB-seconds Lambda (short, spiky, well inside every wall) 2 vCPU-hours Fargate (past the 900 s wall; or split it per region) 3 vCPU-hours Fargate (steady all day, so the meter runs anyway) 4 bytes scanned Athena (pays only when someone asks; lay out the data) 5 RPU or bytes decide by count: 288 refreshes a day; analyst session 6

Price the close calls. For any job near a boundary, write the one-line sum from Part 3: cost of one run, times runs a month, against the always-on month. Mark the trigger that would reopen the choice, such as "past 600 seconds" or "past about 108,000 runs a month for this shape".

Write one sentence per job. "This runs on Lambda because it is short and spiky, and we revisit it if a run passes 600 seconds." The sentence is what survives into the design review; the table is how you got there. Bring it to session 6, where it becomes the engines row of the one-page platform.

★ Worked example: the sentence for job 2 (constructed)Nightly reconciliation moves to a Fargate task that runs and stops, because one run already takes 22 minutes and Lambda stops at 900 s. Revisit if it can be split into per-region runs under 10 minutes each.
✗ The sheet that picks the engine firsteverything: "we are a serverless shop", so Lambda long jobs: raise the timeout (it cannot go past 900 s) dashboards: a container polling the warehouse every 5 minutes always-on: nobody checks how much of the day it works

Ask the idle question. For every always-on service in the sheet, write down roughly how many minutes of each day it does real work. If the answer is "twenty seconds", the meter is wrong, whatever the engine's reputation. If the answer is "most of the day", a container is the honest choice and nobody should feel they failed a serverless test.

Homework

Before session 5

30 min
  1. Find the longest function. Ask your platform owner for the Lambda function whose longest run in the last month came closest to 900 seconds, and whether anything alarms before it reaches the wall.
  2. Find the idlest container. Ask for the always-on service that does the least work per day. Price it with Part 3's method against the same work run as a function.
  3. Find the warehouse's quiet hours. If you run Redshift Serverless, ask whether anything keeps a connection pool open overnight, and whether cancelled queries show up in the bill.

Check yourself

Three questions

Clear all three and leader session 4 gets stamped in your passport.

1 · A team proposes running a job that takes 20 minutes as a single Lambda function, with 10 GB of memory to be safe. What is wrong with the plan?

The "Lambda quotas" page gives the timeout as "900 seconds (15 minutes)." Memory runs from 128 MB to 10,240 MB and buys CPU, not time. A run past the wall is stopped, whatever its memory.

2 · Redshift Serverless bills "in RPU-hours on a per-second basis, with a 60-second minimum charge." What does that mean for a 5-second query on an idle 8 RPU warehouse?

Per-second billing with a 60-second floor means short, scattered queries each pay for a minute. The 8 RPU figures are analyst session 6's model at $0.375 per RPU-hour; re-verify the price before relying on it. Idle time with no queries is not billed for compute.

3 · An executive dashboard refreshes a SQL query against the lake every 5 minutes. Which meter should the team be comparing?

A SQL question is priced by a query engine, not by compute you run yourself. Analyst session 6 models the break-even at about 31 queries a day against one busy warehouse hour and about 123 against four (modelled; your numbers will differ). Session 5 shows how layout changes the bytes side.
