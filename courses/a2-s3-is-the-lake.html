S3 is the lake

Every AWS data platform starts with the same bucket and the same three questions: how are the keys named, which storage class does each kind of data sit in, and what happens to it after thirty days, a year, seven years. Part 0

Where we start

Session 1 put S3 at the bottom of the map as "the files themselves". Tonight that row gets real. S3 looks like a file system in the console, with folders you can click into, but underneath it is a flat list of keys, and almost every decision a data leader makes about the lake is really a decision about how those keys are named. Get the naming right and permissions, lifecycle rules and query engines all have something clean to point at. Get it wrong and every later fix is a rename of millions of objects.

Part 1 · covers buckets, keys, prefixes and zones

No folders, only keys

5 min live

A bucket holds objects, and each object has one key: a single string such as curated/nyc_taxi/pickup_date=2024-01-15/data_0.parquet. The slashes are just characters. A prefix is the start of a key, curated/ or curated/nyc_taxi/, and it is the unit the rest of AWS points at: a policy grants access to a prefix, a lifecycle rule filters on a prefix, an Athena table's location is a prefix. That is why the first design decision for a lake is the top-level prefixes, the zones.

LiveThree zones, three kinds of reader2 min▶

raw/ holds data exactly as it arrived: the CSV export, the JSON dump, never edited. Only the ingest process writes here, and almost nobody reads it. curated/ holds the cleaned, typed version, usually Parquet laid out by date, and it is what analysts and dashboards query. archive/ holds what you must keep but rarely touch, such as old raw files kept for an audit or a legal hold. The names vary from team to team; the separation does not. Each zone has a different reader, a different access rule, and, as Part 2 shows, a different right storage class.

How the curated files are built from the raw ones is a pipeline question, and pipelines have their own home in learn data engineering. Here the only question is where each kind of file lives and what that costs.

LiveWhy the prefix carries the weight2 min▶

S3 performance is also counted per prefix. The Amazon S3 User Guide says an application "can achieve at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix", and "There are no limits to the number of prefixes in a bucket." Spreading heavy reads across more prefixes, such as one per day, spreads the load. While S3 is scaling up to a new request rate, it may answer some requests with 503 Slow Down errors, so a sudden burst should retry rather than fail.

One more property removes a whole class of old worries: S3 "provides strong read-after-write consistency for PUT and DELETE requests of objects in your Amazon S3 bucket in all AWS Regions." A job that writes a file and immediately lists the prefix will see it. Bucket configurations, such as policies and lifecycle rules, are the exception: they are eventually consistent, so a just-changed rule may take a moment to apply.

Self-studyThe console's folders are a drawing of the keys1 min▶

The S3 console groups keys at each slash and shows the groups as folders, which is helpful for browsing and misleading for design. There is no folder object to rename, move or lock. "Renaming a folder" means copying every object under the old prefix to a new key and deleting the original, which is billed per request (S3 PUT, COPY, POST and LIST requests are $0.005 per 1,000 in us-east-1, AWS Price List, 3 October 2026; re-verify before relying on it). That is the practical reason to fix the zone names before the first terabyte lands.

Real world

The shared "data/" prefix nobody could split. A team starts with everything under one prefix, data/, raw exports and cleaned tables side by side with names like data/orders_2024.csv and data/orders_clean.parquet. A year later the security lead asks for analysts to see curated tables only. There is no prefix that means "curated", so the policy would have to list hundreds of individual keys and be edited every week. The real fix is a migration into raw/ and curated/, paid for in copy requests and a weekend. The scenario is constructed; the shape is common.

Part 2 · covers storage classes and their minimums

Cheaper per gigabyte, slower and stickier

6 min live

Every object in S3 sits in a storage class, and "If you don't specify the storage class when you upload an object, Amazon S3 assigns the S3 Standard storage class." All the classes below are designed for eleven nines of durability, so they do not differ in how likely you are to lose a byte. They differ in availability, in how many Availability Zones hold the copies, in how long you must keep an object before deleting it without a penalty, and in how long it takes to read it back. The price per gigabyte falls as each of those gets worse.

LiveThe minimums are the part that bites2 min▶

Two rules sit underneath the cheap classes. The first is the minimum billable size: "If an object is less than 128 KB, Amazon S3 charges you for 128 KB." A lake full of tiny files can pay for far more storage than it holds. The second is the minimum duration: "If you delete an object before the end of the 30-day minimum storage duration period, you are charged for 30 days." Standard-IA and One Zone-IA have a 30-day minimum, Glacier Instant Retrieval and Glacier Flexible Retrieval 90 days, Deep Archive 180 days. Delete a Deep Archive object after a week and you pay for six months.

So the infrequent-access classes are a bet on behaviour, not a discount. They pay off for data that is written once, kept for months and read rarely. They lose for data that churns, gets rewritten nightly, or is read in full every day, because Standard-IA also charges $0.01 per GB retrieved (us-east-1, AWS Price List, 3 October 2026).

LiveOne Zone means one copy1 min▶

Every class in the table is designed to survive the loss of an Availability Zone except two: One Zone-IA and Express One Zone. AWS's wording for One Zone-IA is that it "is not resilient to the physical loss of the Availability Zone". At $0.01 per GB-month against $0.0125 for Standard-IA, it is the right home for a copy you can rebuild, such as curated Parquet you could regenerate from raw. It is the wrong home for the only copy of anything, and raw data usually is the only copy.

Self-studyIntelligent-Tiering and the retrieval clock3 min▶

Intelligent-Tiering is S3 making the bet for you. "S3 Intelligent-Tiering moves objects that have not been accessed in 30 consecutive days to the Infrequent Access tier", and after 90 days to the Archive Instant Access tier, with "no retrieval fees". The price is a monitoring and automation charge of $0.0025 per 1,000 objects a month (us-east-1, AWS Price List, 3 October 2026; re-verify before relying on it), and one exception that matters to data teams: "If the size of an object is less than 128 KB, it is not monitored and not eligible for auto-tiering." It suits data whose access pattern you genuinely cannot predict. It does nothing for a lake made of small files.

The Glacier classes trade speed for price. Glacier Instant Retrieval returns objects in milliseconds. Glacier Flexible Retrieval takes minutes to 12 hours, depending on the retrieval option. Deep Archive takes 9 to 48 hours: its standard restore typically completes "within 12 hours" and its bulk restore "within 48 hours". Glacier Flexible and Deep Archive objects must be restored before they can be read at all. Before anything goes into those two classes, someone should be able to say out loud: "if the regulator asks, we can answer in two days, and that is fine."

Real world

The Friday audit request. A finance team is asked on a Friday afternoon for raw transaction files from four years ago, due Monday morning. The files are in Deep Archive, which was the right call on cost: $1.01 a terabyte a month against $23.55 in Standard. A standard restore typically completes within 12 hours and a bulk restore within 48, so the request is met, but only because someone started the restore on Friday rather than Monday. The lesson for the plan is a column, not a class: write down who may restore each zone and how long they will wait. The scenario is constructed; the prices and restore times are AWS's.

Part 3 · covers lifecycle rules

Rules that move and delete on a schedule

4 min live

A lifecycle configuration is a set of rules on a bucket, usually filtered by prefix, with two kinds of action. Transition actions "define when objects transition to another storage class." Expiration actions "define when objects expire. Amazon S3 deletes expired objects on your behalf." The rules apply "to both existing objects and objects that you add later", so a new rule reaches the whole history of a prefix the day it is saved. The Well-Architected Data Analytics Lens puts the practice plainly: "If data is stored in Amazon S3, use Amazon S3 Lifecycle configurations to expire data automatically" (BP 13.1).

LiveFive rules of the waterfall3 min▶

Downhill only. "Amazon S3 supports a waterfall model for transitioning between storage classes": Standard can move to any lower class, Standard-IA to Intelligent-Tiering, One Zone-IA, either Glacier class or Deep Archive, Glacier Instant Retrieval to Glacier Flexible or Deep Archive, Glacier Flexible to Deep Archive. Deep Archive is the floor. "The transition of objects to the S3 Glacier Deep Archive storage class can go only one way." No lifecycle rule brings it back up.

Small objects stay put. "Starting September 2024, the default behavior prevents objects smaller than 128 KB from being transitioned to any storage class." A rule on a prefix of small files can run for a year and move nothing. Early exits are billed. "If you transition objects out of these storage classes before the minimum duration, you are charged for the remainder of that duration." AWS's own worked example uses Glacier Instant Retrieval's 90-day minimum to show that a later move to Deep Archive "must occur after at least 94 days." Policies cannot stop it. "You can't use a bucket policy to prevent deletions or transitions by an S3 Lifecycle rule." Whoever can edit the lifecycle configuration can delete a zone on a schedule, which is why session 3 treats that permission as a sensitive one.

Self-studyThe 30-day example is an example, not a law2 min▶

Many guides say objects "must" sit in Standard for 30 days before a lifecycle rule can move them to Standard-IA. The pages read for these sessions, the S3 User Guide's lifecycle overview, its transition considerations and its configuration examples, do not state that as a rule. What they do state is the 30-day minimum storage charge for Standard-IA, and an example rule: "Transition objects to the S3 Standard-IA storage class 30 days after creation." Treat 30 days as a sensible starting point that matches the minimum charge, not as a constraint AWS imposes, and check the current documentation if a design depends on moving data sooner.

The same Lens that recommends lifecycle rules also notes that "Using Parquet over CSV format can reduce storage costs significantly" (BP 13.1.6). The Lens was last updated on 22 December 2023, so read it as principles rather than a current feature list. File formats in depth belong to learn AI infra; here the point is only that a smaller file is a smaller bill in every class.

Real world

The curated zone that a lifecycle rule would never move. Analyst session 1 lays out 100,000 real New York taxi trips from January 2024 as Parquet partitioned by pickup day: 31 files of 73,785 to 113,419 bytes each. Every one of them is under 128 KB. Point a default lifecycle rule at that prefix and nothing transitions; point Intelligent-Tiering at it and nothing is monitored. At full scale the daily files would be larger, so this is a property of the sample, not of partitioning, but it is exactly what happens to a lake that partitions too finely. The file sizes are measured; the rule outcome follows from AWS's September 2024 default.

Build-along

A lifecycle plan on paper

★ 22 min · everyone builds

No console and no account. One sheet, five columns, one row per top-level prefix. By the end you have a plan an engineer can turn into a lifecycle configuration in an afternoon, and a price for each row. The worked example below is constructed: your volumes, prefixes and retention periods will differ, and so will your numbers.

List your top-level prefixes and who touches each. If your lake has no zones yet, start from raw, curated and archive. For each, write the writer, the readers, and whether the data could be rebuilt from somewhere else. That last answer decides more than any price.

★ Worked example, zones (constructed)raw/ written by: ingest job read by: almost nobody rebuildable: NO, only copy curated/ written by: transform job read by: analysts, BI rebuildable: yes, from raw/ archive/ written by: platform team read by: auditors, rarely rebuildable: NO, legal hold

Pick the class each prefix is written to. Default is S3 Standard. Anything read daily stays in Standard, because the infrequent-access classes charge to read it. Only a rebuildable copy may sit in a One Zone class.

★ Worked example, class at write (constructed)raw/ S3 Standard (fresh files get re-read for a few weeks) curated/ S3 Standard (queried every day; IA would charge per GB read) archive/ Glacier Instant Retrieval (if an auditor needs it in milliseconds) or Deep Archive (if the answer can wait 9 to 48 hours)

Write the transitions, then check them against the minimums. Each step must leave the data in its class at least as long as that class's minimum, or you pay the rest anyway. Then check file sizes: anything under 128 KB will not transition by default.

★ Worked example, raw/ transitions (constructed)day 0 S3 Standard day 30 -> Standard-IA (30-day minimum: stays until day 180, so 150 days, fine) day 180 -> Deep Archive (180-day minimum: stays until year 7, fine) one way: nothing moves back up without a restore check: raw files are monthly CSVs, far above 128 KB, so they will transition

Write the expiration and the restorer. An expiration is a scheduled delete that no bucket policy can block, so it needs a named retention reason. The restorer is a person or role, plus the wait they have agreed to.

★ Worked example, expiration and restore (constructed)raw/ expire after 7 years (retention policy ref. needed) restore: platform lead, 9 to 48 h curated/ no expiration; rebuilt from raw/ if lost restore: not needed archive/ expire when the legal hold lifts, set by legal restore: platform lead on legal's request

Price each row for one terabyte. Use the per-terabyte numbers from Part 2 and say where they came from. This is the line that goes into the budget conversation.

★ The price line, per 1,024 GB for one monthS3 Standard: $23.55 Standard-IA: $12.80 (plus $0.01 per GB read back) Glacier Instant Retrieval: $4.10 Glacier Flexible: $3.69 Deep Archive: $1.01 (180-day minimum, 9 to 48 h to read) (us-east-1, AWS Price List, 3 October 2026; re-verify before relying on it)
✗ The plan that saves money and loses dataeverything older than 30 days -> One Zone-IA expire everything after 1 year whoever needs old data can just restore it

Plan by reader, not by age. A lifecycle rule only knows how old an object is. You know who reads it. Write the reader column first, and the transitions almost write themselves: data nobody reads moves down, data everybody reads stays in Standard, and the only copy never goes to one zone.

Homework

Before session 3

30 min
  1. List the top-level prefixes of one real bucket your team uses, or would use. If there is one catch-all prefix such as data/, write down what it would take to split it.
  2. Find the only copies. For each zone, answer: if this prefix vanished tomorrow, could we rebuild it? Any "no" must not live in a One Zone class.
  3. Find the existing lifecycle rules. Ask your platform team whether any bucket has one, what it does, and who can edit it. A rule nobody remembers is a scheduled delete nobody owns.
  4. Bring the restore column. For your archive, write who may restore and how long they can wait. Session 3 turns "who may" into IAM policies.
Check yourself

Three questions

Clear all three and leader session 2 gets stamped in your passport.

1 · An engineer says "just rename the curated folder to gold". What is actually involved in S3?

A key is one string and a prefix is just its start. The console draws folders, but a rename is a copy plus a delete for every object, billed per request, and every policy, rule and table that named the old prefix must change too.

2 · You have raw files that exist nowhere else, and a curated Parquet copy you can regenerate from them. Which pairing is sound?

One Zone-IA "is not resilient to the physical loss of the Availability Zone". That trade suits a copy you can regenerate and never suits the only copy. Curated data read every day belongs in Standard anyway, because the IA classes charge per GB read.

3 · A team writes 1 TB to Standard-IA, realises it was the wrong data, and deletes it after 10 days. What do they pay for storage?

AWS: "If you delete an object before the end of the 30-day minimum storage duration period, you are charged for 30 days." The minimums are why the cheap classes suit data that settles, not data that churns.
