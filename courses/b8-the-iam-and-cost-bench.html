The IAM and cost bench

Two questions decide whether an AWS data platform is safe and affordable: will this request be allowed, and what will this query cost? Tonight both are computed in your browser instead of argued. The first half is a policy evaluator written to AWS's documented evaluation logic and checked against 36 cases taken from the documentation, with an anti-lever that shows what one wildcard does and break buttons that prove the tests can fail. The second half prices queries and storage from the AWS Price List, with bytes measured on the real taxi files from session 1.

Where we start

A bench is a fixed set of inputs and a fixed question, so that when two choices give two answers the only thing that differed was the choice. The IAM half has 36 requests, each with the verdict AWS's documentation says it must get. The cost half has four questions asked of the same 100,000 real taxi trips in three layouts. Part 1 · covers the evaluation order the evaluator implements

Six steps, in AWS's order

6 min live

AWS's enforcement logic starts from no: "By default, all requests are implicitly denied", the account root user excepted. It then looks for any explicit Deny in every applicable policy, and "If the enforcement code finds even one explicit deny that applies", the answer is Deny. Only after that does it look for something that allows the request. The evaluator on this page follows those steps for one stated scope: an IAM user in a single account.

LiveWhat the evaluator does, and refuses to do3 min▶

It reads identity policies, an optional bucket policy with a Principal, an optional permissions boundary and an optional SCP. It matches actions case-insensitively with * and ?, because "The prefix and the action name are case insensitive", and resources case-sensitively, segment by segment. It implements NotAction and six condition operators: StringEquals, StringNotEquals, StringLike, IpAddress, NotIpAddress and Bool. A key missing from the request makes a condition false, and a negated one true, as the operator page states. Several operators are ANDed, several values for one key are ORed.

It does not implement session policies, resource control policies, role sessions, cross-account requests, policy variables or the ForAllValues and ForAnyValue set operators. Those are not small details, they change verdicts, so the evaluator throws an error on an operator it does not know rather than quietly guessing. The same logic is ported to Python, and on all 192 verdicts the bench computes (36 cases in four modes, plus 24 analyst actions twice) the browser and Python agree.

Self-studyWhere the 36 expected verdicts come from2 min▶

Each case quotes the documentation sentence it tests. Some are straight from AWS's own tables: bucket/*/test/* must match bucket/1/2/test/3/object.jpg and must not match bucket/1-test/object.jpg; a Bool deny on aws:SecureTransport = false must match a plain-HTTP request and must not match when the key is absent. Others follow from the evaluation pages: a boundary is an intersection, an SCP must also allow, and a bucket policy that names an IAM user is "not limited by an implicit deny in an identity-based policy or permissions boundary". The table is in the widget; expand any row to read its rule.

Build-along · the IAM half

Ask as the analyst, then break the logic

★ 12 min · the main event, part one

The analyst holds two policies: read the curated zone, run Athena, write query results; and guardrails that deny plain HTTP on the lake and deny deleting the bucket or changing its policy. The request starts on s3:PutObject into curated, which nothing allows. Read the trace, then switch on the anti-lever and read it again. Then run the two break buttons and watch the test table catch each one.

Read it in this order. The verdict, then which step decided it, then the count beside the anti-lever. Set "Over TLS" to plain HTTP on any S3 request to the lake and watch step 1 end the evaluation, wildcard or not.

Part 2 · covers the anti-lever and the break buttons

One wildcard, and two ways to be wrong

5 min live

The anti-lever is the most common shortcut in real accounts: an Allow for "Action": "*" on "Resource": "*", added because something was denied and a deadline was close. The break buttons are the opposite test: they make the evaluator wrong on purpose, so you can see that the 36 cases measure the logic and do not merely agree with it.

LiveThe anti-lever, with its honest nuance2 min▶

With "Action": "*" added, the denied request, s3:PutObject into curated, passes. So do 14 other actions the analyst never needed, among them deleting curated objects, deleting Glue tables, updating the ingest Lambda's code, creating IAM users and access keys, starting EC2 instances, decrypting with KMS, and reading another bucket. On the 36-case table, allowed requests rise from 16 to 28, and only 24 of 36 verdicts still match what the documentation says the original policies should produce.

The nuance matters: the wildcard does not beat the two explicit Denies. DeleteBucket and PutBucketPolicy stay denied, because step 1 runs before any Allow is read. That is the real lesson of the guardrails policy: explicit Denies are the floor a hurried wildcard cannot lower. It is also why least privilege is a practice and not a slogan; AWS's guidance is to "grant only the permissions required to perform a task", and IAM Access Analyzer can generate a policy from what a role actually used. The concepts behind that, roles, attributes and access reviews, are taught in data access control.

LiveWhat the break buttons prove2 min▶

Allow beats Deny fails exactly the 6 cases where an explicit Deny meets an Allow: the DeleteObject guard, the plain-HTTP guard, the bucket policy deny, the SCP deny, the boundary deny and the office-IP fence. A missing key matches fails 2: a tag-gated Allow that would let an untagged user in, and the HTTPS guard that would block a request carrying no transport key. If either button had left the score at 36, the cases would be decoration. They are not: each break is caught by the cases written for it, and by nothing else.

Build-along · the cost half

Price a query at your size

★ 14 min · the main event, part two

Set your table size as if it were stored as CSV, how many times a day the question runs, and a storage class. Pick one of the four questions, or build your own from columns and days. The bench reads the measured bytes for each layout, scales them to your size, and prices them from the Price List rows shown in the stamp.

Read it in this order. The share of the CSV first, because it does not depend on prices, then the monthly cost, then storage. Try Q1, every column, and notice the partitioned layout is the more expensive Parquet: the small-files trade from session 1, priced.

LiveFinding 1: below 10 MB, every layout costs the same2 min▶

Athena bills "the number of bytes scanned per query, rounded up to the nearest megabyte, with a 10 MB minimum per query". The whole sample is under 10 MB as CSV, so on the real files every query in every layout bills the minimum, $0.000048. That is why layout mistakes survive proofs of concept: on a small table they are free. The difference appears only at scale, which is the job of the size box.

LiveFinding 2: no layout wins every question2 min▶

The single Parquet file wins the two whole-month questions; the partitioned layout wins the two date-filtered ones by a factor of 13 to 92 over the single file. The right layout follows the questions people actually ask, which is why session 4 starts from the query log. The partitioned layout's whole-month penalty is partly a sample artefact: 31 files of about 100 kilobytes each carry proportionally heavy footers, and linear scaling carries that weight up to 1 TB, where real daily files would be far larger. Read Q1 and Q2 for partitioned as an upper bound.

Self-studyWhat the panel does not price2 min▶

S3 GET request charges for the files Athena opens, Glue catalog requests, data transfer, query result storage, and the Intelligent-Tiering monitoring fee are not in the totals. At these sizes the scan dominates them, but a table with millions of tiny files can make request charges visible. Storage minimums matter too: Standard-IA and Glacier Instant Retrieval bill at least 128 KB per object and at least 30 or 90 days, so a class that looks cheaper in the panel can cost more for short-lived data.

Check yourself

Three questions

Clear all three and analyst session 8 gets stamped in your passport.

1 · The analyst's guardrail denies s3:DeleteBucket. Someone adds an Allow for "Action": "*" on "Resource": "*". What happens to DeleteBucket?

"An explicit deny overrides an explicit allow." The wildcard still hands over 15 other actions, which is why the guardrail is necessary but not enough.

2 · Breaking the evaluator so that an Allow beats a Deny makes 6 of the 36 cases fail. Why is that a good result?

A test suite that cannot fail measures nothing. Breaking the rule and watching the right cases fail is how you know the passing score means something.

3 · On the real 100,000-row sample, every query in every layout bills $0.000048. At 1,024 GB the one-week question costs $15,000 a month as CSV and $88 partitioned. What explains both?

The minimum makes small tables look free, which is why layout mistakes survive proofs of concept. The scaling is modelled, the share is measured, and the price is $5.00 per TB from the Price List.
