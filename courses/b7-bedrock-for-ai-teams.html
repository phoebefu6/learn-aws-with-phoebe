Bedrock for AI teams

Sooner or later someone on the data team is asked to "just run the model over the notes". On AWS that usually means Bedrock: managed access to foundation models, billed per token, behind the same IAM that guards the lake. Tonight we build a real Converse request and let botocore check it against Bedrock's own schema without calling any model, price a million short notes on demand and in batch, and write the policy that lets one role call one model. Then we read the data-retention page all the way to the caveat most teams skip.

Part 1 · covers what Bedrock is today

A managed front door to many models

5 min live

The Bedrock User Guide, "What is Amazon Bedrock?", opens with "a fully managed service that provides secure, enterprise-grade access to high-performing foundation models", and says it "supports 100+ foundation models". Your code does not host a model, size a GPU or patch a server. It sends a request to the bedrock-runtime endpoint, IAM decides whether your role may call that model, and you pay for the tokens. Everything else on the platform, retrieval, safeguards, customization, batch jobs, is an optional layer around that one call.

LiveWhat the overview says now, and what it stopped saying2 min▶

Bedrock is "a fully managed service that provides secure, enterprise-grade access to high-performing foundation models from leading AI companies", and it "supports 100+ foundation models from industry-leading providers". Those are the two sentences to quote. One phrase you may remember from older slides, Bedrock as a "single API", is no longer on the overview page, and neither is a tidy bullet list of capabilities; each capability below was read on its own page. Older decks are not wrong about history, they are just not the current page, so quote the current one.

For an analyst the working idea is simple: the provider trained the model, AWS runs it, and you rent it a request at a time. Which models are offered in which Region changes often enough that AWS tells you to check, and so do these pages: re-verify model availability before you plan around one.

LiveConverse: one request shape you can reuse2 min▶

The build-along calls the converse operation on a bedrock-runtime client. Its request is a model ID, a list of messages, each with a role and a list of content blocks, and an optional inferenceConfig such as maxTokens and temperature. The point of Converse is that this messages shape stays the same across the models that support it, so switching from one model to another is mostly a change of modelId, not a rewrite of your request code. Support is per model, and so are some features: check the model you choose before you rely on it.

Keep one distinction from session 2 in mind. Converse is an API operation. It is not, as Part 3 shows, the name of an IAM action.

Self-studyThe four optional layers, in one line each3 min▶
  • Knowledge Bases. Bedrock's RAG layer. The guide: "RAG is a technique that uses information from data sources to improve the relevancy and accuracy of generated responses."
  • Guardrails. "Amazon Bedrock Guardrails provides configurable safeguards to help you build safe generative AI applications."
  • Model customization. "the process of providing training data to a model to improve its performance for specific use-cases", by supervised fine-tuning, reinforcement fine-tuning or distillation.
  • Batch inference. "With batch inference, you can submit multiple prompts and generate responses asynchronously." One limit worth knowing early: "Batch inference isn't supported for provisioned models."

And one that is closing: "Amazon Bedrock Agents (now Amazon Bedrock Agents Classic) is no longer open to new customers." The named successor is Amazon Bedrock AgentCore. If a design document written before that change says "we will use Bedrock Agents", it needs a second look. How to serve and scale models on your own GPUs is a different subject, taught in learn-ai-infra; tracking, versioning and promoting models belongs to learn-dataops; Claude on Bedrock specifically is covered in learn-claude session 68.

Real world

The plan built on last year's blog post. A team scopes a support assistant around Bedrock Agents, working from a tutorial that was accurate when it was written. In the new account the Agents console tells them what the user guide now says: Agents Classic is no longer open to new customers, and AgentCore is the successor. Two weeks of design assumed a door that had closed. The fix is cheap if it happens on day one: read the current user guide page for every capability in the plan before anyone draws boxes. The scenario is constructed; the Agents Classic sentence is quoted from the Amazon Bedrock User Guide.

Part 2 · covers the token bill

Tokens in, tokens out, and when to wait for half price

6 min live

Bedrock bills per token, and input and output are priced separately. Amazon Nova Micro on demand is $0.000035 per 1,000 input tokens and $0.00014 per 1,000 output tokens; in batch, $0.0000175 and $0.00007. All of these are us-east-1, AWS Price List, 3 October 2026, and prices change, so re-verify them before relying on them. The build-along applies them to a classification job: a million short notes, 120 tokens in and 8 tokens out each. Those volumes are an assumption, not a measurement; your numbers will differ.

LiveRead the bill from the inside3 min▶

Per note, 120 input tokens at $0.000035 per 1,000 is $0.0000042, and 8 output tokens at $0.00014 per 1,000 is $0.00000112. Add them and multiply by a million: $5.32 on demand. Two things jump out.

  • Input dominates here. Output tokens cost four times as much each, but a classifier writes almost nothing back, so $4.20 of the $5.32 is input. Trim the prompt and the bill moves; trim the answer and it barely does. A summariser, which writes long answers, would flip that balance.
  • Batch is exactly half. The pricing page: batch inference is offered "at a 50% lower price compared to on-demand inference pricing". The batch rates in the Price List are half the on-demand ones, so the same job is $2.66.

All modelled: real prices (us-east-1, AWS Price List, 3 October 2026; re-verify), assumed volumes and token counts. A real tokenizer will count your notes differently, so measure a sample before you quote a total.

LiveOn demand, batch, Flex or Priority3 min▶

The pricing page lists "a variety of tiers including Standard, Flex, Priority, and Reserved tiers". Its footnotes give the two you will be asked about: "Flex tier pricing is at 50% discount to Standard tier pricing" and "Priority tier pricing is at 75% premium to Standard tier pricing". Batch is a separate route, a job you submit and collect later, at 50% below on demand.

The decision is about waiting, not about the model. A backlog of a million notes that nobody reads until Monday does not need an answer in a second, so batch halves it for free. A chatbot answering a customer cannot wait for a job to finish. Which tiers a given model offers, and their exact rates for it, were not verified on these pages: check the pricing page for your model before you plan on Flex or Priority.

Self-studyWhere the cheaper model fits2 min▶

The Price List also carries Nova Lite at $0.00006 per 1,000 input tokens and $0.00024 per 1,000 output, both on demand (us-east-1, AWS Price List, 3 October 2026; re-verify). That is a little under twice Nova Micro's rates. Whether the extra quality is worth it for your notes is not a price question: it is an evaluation you run on a labelled sample, and these pages did not run one. The useful habit is to price both before the evaluation, so the team knows what a better answer has to be worth. How to track those evaluation runs and promote a model choice is the territory of learn-dataops.

Real world

The backlog that ran on demand overnight. An analyst is asked to tag a year of support notes by Monday. She writes a loop that calls the model one note at a time, leaves it running over the weekend, and it works. Nobody needed the answers before Monday morning, which is exactly the shape batch inference exists for: submit the prompts as one job, collect the responses later, pay half. On the modelled million notes that is $5.32 against $2.66, small money; at a hundred times the volume, or with a model priced many times higher, it is a line someone will ask about. The scenario is constructed; your numbers will differ.

Part 3 · covers least privilege and your data

Let one role call one model, and know where the prompt goes

4 min live

Here is the fact that trips up teams writing their first Bedrock policy: there is no bedrock:Converse IAM action. The AWS service reference for Bedrock lists 262 actions, and for inference it lists InvokeModel and InvokeModelWithResponseStream. A Converse call is authorised by bedrock:InvokeModel. So a least-privilege policy names that action and one foundation-model ARN, and nothing else. Then comes the second question every security reviewer asks: what happens to the prompt?

LiveThe policy, and the action it has to name2 min▶

The build-along prints the statement that matters:

★ One model only{"Sid": "OneModelOnly", "Effect": "Allow", "Action": ["bedrock:InvokeModel"], "Resource": "arn:aws:bedrock:us-east-1::foundation-model/amazon.nova-micro-v1:0"}

Notice the empty account field in the ARN, the :: after the Region: foundation models belong to no customer account. If someone writes "Action": "bedrock:Converse", the policy names an action the service reference does not list, so it grants nothing, and every call fails with access denied while the author swears the policy is attached. If the team streams replies with the streaming variant of the call, add bedrock:InvokeModelWithResponseStream on the same ARN, and only then.

Session 8's bench already holds the proof of the default. Its analyst role, analyst-lake-read, is checked against 24 data-team actions, and one of them is bedrock:InvokeModel on this exact Nova Micro ARN. The role allows 7 of the 24, none of them Bedrock: implicit deny. The concepts behind giving each workload its own narrow role are taught in learn-data-access-control; here we only write the JSON.

LiveWhat happens to the prompt: teach both halves2 min▶

The reassuring half, from "Data protection" and the Bedrock FAQs: model providers "don't have access to Amazon Bedrock logs or to customer prompts and completions", and "With Amazon Bedrock, your content is not used to improve the base models and is not shared with any model providers." The FAQs add that AWS and the providers "will not use any inputs to or outputs from Amazon Bedrock to train Amazon Nova, Amazon Titan, or any third-party models."

The half that gets dropped from slides, from "Data retention": for some models, prompts and completions "are retained within the AWS boundary for up to 30 days and may be reviewed by AWS". Both statements are true at once. Providers do not see your prompts, and your content does not train base models; and for certain models AWS itself keeps them for up to 30 days and may review them. These pages did not record which models carry that retention, and the list can change, so read the "Data retention" page for the exact model you plan to send sensitive notes to, before you send them.

Self-studyWhat the mock and the stub cannot tell you2 min▶

The build-along proves your request has the right shape, because botocore checks it against the Bedrock API model shipped inside the library. It does not prove the call would be authorised: no IAM engine runs, and the dummy keys would be rejected by real AWS. It does not prove the model is enabled in your account, or available in your Region. And the reply is a canned string, so it proves nothing about what the model would say. Session 2's moto run had the same honesty problem from the other side: moto's IAM enforcement is a teaching aid, not AWS's engine. Session 8's bench is where the policy evaluation is checked against the documented rules, case by case.

Real world

The team that assumed AWS never keeps prompts. A team pastes the "not shared with any model providers" sentence into its data-protection review and sends customer complaint text to a model, satisfied that nobody else will see it. A reviewer later reads the "Data retention" page and finds that for some models AWS retains prompts and completions for up to 30 days and may review them. Nothing leaked and no rule was broken, but the review had promised more than the documentation does, and it had to be reopened. The fix was to quote both sentences and name the model checked. The scenario is constructed; both sentences are quoted from the Amazon Bedrock User Guide and FAQs.

Build-along

A checked request, a cost and a policy, with no model called

★ 22 min · everyone builds

One Python file, about forty lines, using the boto3 you installed in session 1. It builds a real Converse request for Nova Micro and hands it to botocore's Stubber: botocore validates every field against Bedrock's real API schema, and the Stubber answers with a reply that is fake and says STUBBED in its own text. Then it sends a deliberately broken request to see the schema catch it, prices the million-note job, and prints the one-model policy. The output below is pasted from a real run of exactly this code. Before you run it, guess which of the two requests botocore rejects, and why.

Reuse the environment from analyst session 1. Same folder, same .venv, with boto3 and botocore 1.43.108 already installed. This script reads no files and needs no AWS account; the access keys in it are the literal string x. It was run on Python 3.11.11.

★ Step 1 · setup (verified 3 October 2026). .venv/bin/activate python -c "import boto3, botocore; print(boto3.__version__, botocore.__version__)" # expect 1.43.108 1.43.108

Build the client and the request. A bedrock-runtime client in us-east-1 with dummy keys, and a Converse request: the model ID, one user message whose content is a list of blocks, and an inferenceConfig that caps the reply at 20 tokens with temperature 0, which is what you want from a classifier.

★ Step 2 · b7_bedrock.py, part 1# Analyst session 7 - Bedrock for AI teams. No model is called: botocore checks the request against # Bedrock's real API schema, and a Stubber stands in for the response (clearly fake). import json, boto3 from botocore.stub import Stubber MODEL = "amazon.nova-micro-v1:0" rt = boto3.client("bedrock-runtime", region_name="us-east-1", aws_access_key_id="x", aws_secret_access_key="x") request = { "modelId": MODEL, "messages": [{"role": "user", "content": [{"text": "Classify this trip note as fare_dispute, lost_item or other: 'driver kept my umbrella'"}]}], "inferenceConfig": {"maxTokens": 20, "temperature": 0}, }

Let botocore check it, and break it on purpose. Inside the with Stubber(rt) block, botocore validates the request against Bedrock's real Converse schema, and the Stubber also asserts that the call matches the request it was told to expect. Only then does it hand back the canned reply, which says STUBBED in its own text so nobody mistakes it for a model's answer. The usage numbers in the stub are made up too. The second call passes content as a plain string, which the schema forbids.

★ Step 3 · b7_bedrock.py, part 2with Stubber(rt) as stub: stub.add_response("converse", { "output": {"message": {"role": "assistant", "content": [{"text": "lost_item (STUBBED, not a model output)"}]}}, "stopReason": "end_turn", "usage": {"inputTokens": 31, "outputTokens": 4, "totalTokens": 35}, "metrics": {"latencyMs": 0}, }, request) r = rt.converse(**request) print("request accepted by the Converse schema; stubbed reply:", r["output"]["message"]["content"][0]["text"]) try: rt.converse(modelId=MODEL, messages=[{"role": "user", "content": "plain string"}]) except Exception as e: print("schema check catches a malformed request:", type(e).__name__)

Check yourself

Three questions

Clear all three and analyst session 7 gets stamped in your passport.

1 · A role must be allowed to make Converse calls to Nova Micro and nothing else. Which IAM action does the policy name?

There is no bedrock:Converse IAM action. The AWS service reference lists 262 Bedrock actions, with InvokeModel and InvokeModelWithResponseStream for inference, so Converse is authorised by bedrock:InvokeModel, scoped to one ARN.

2 · A million notes must be tagged by Monday, and nobody reads the tags before then. On demand, the modelled job is $5.32. What does batch inference change?

The pricing page offers batch "at a 50% lower price compared to on-demand inference pricing", and the batch rates in the Price List are half the on-demand ones. Same model, same tokens, a job you collect later (modelled volumes; us-east-1, AWS Price List, 3 October 2026).

3 · A review states: "AWS never keeps our prompts." What do the Bedrock documents actually support?

Both halves are on the record. "Data protection" and the FAQs: providers have no access to prompts and completions, and content is not used to improve base models. "Data retention": for some models they "are retained within the AWS boundary for up to 30 days and may be reviewed by AWS". Check the page for your model.
