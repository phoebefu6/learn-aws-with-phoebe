Athena: pay per byte scanned

Athena has no servers to size and no clock to watch. It has one meter: how many bytes a query reads from S3. That makes the layout decisions from session 1 into prices. Tonight we read Athena's billing rules line by line, ask the same three questions of the CSV, the Parquet file and the partitioned copy, and count the bytes each one has to fetch. The answers never change. The byte counts change by a factor of more than a thousand.

Where we start

Session 1 wrote the same 100,000 taxi trips three ways into an out/ folder. Session 3 told the catalog what those files are: 19 columns, partition key pickup_date, 31 partitions. Part 1 · covers how Athena bills a query

The meter counts bytes, not seconds

5 min live

Athena charges $5.00 per TB scanned (us-east-1, AWS Price List, 3 October 2026; prices change without notice, so re-verify before relying on them). The pricing page states the rule exactly: "You are charged for the number of bytes scanned per query, rounded up to the nearest megabyte, with a 10 MB minimum per query." A slow query and a fast query that read the same bytes cost the same. A query that reads twice the bytes costs twice as much, whatever it returns.

LiveFour rules from the pricing page3 min▶

Rounding and the floor. Bytes are "rounded up to the nearest megabyte, with a 10 MB minimum per query". Ten megabytes at $5.00 per TB is $0.000048, the smallest Athena bill there is. What is free. "There are no charges for Data Definition Language (DDL) statements like CREATE, ALTER, or DROP TABLE statements for managing partitions, or failed queries." Registering a table costs nothing; a query that errors costs nothing. What is not. "Canceled queries are billed for the total amount of data scanned when the query is canceled." Pressing cancel stops the meter; it does not refund it. Compression. The Athena tuning guide says "you pay for the number of bytes scanned before decompression", so compressed bytes in S3 are the bytes you pay for, and smaller files are a direct discount.

The pricing page puts the combined effect of good layout at "up to 90%" saved per query from "compressing, partitioning, and converting your data into columnar formats". Part 2 measures what that looks like on real data, question by question.

Self-studyWhat a megabyte means here2 min▶

The build-along script counts a megabyte as 220 bytes (1,048,576) and a terabyte as 240. The pricing page says "megabyte" and "TB" without defining either, and these pages could not find a definition at source, so treat the unit as a convention of the script, not a fact about Athena. It matters at exactly one point tonight: the CSV is 10,095,345 bytes, which is under 10 binary megabytes (10,485,760 bytes) and just over 10 decimal ones. Under the script's convention it sits on the floor with everything else. Under the other reading it would round up to 11 MB. Either way the bill is well under a hundredth of a cent, and the comparison between layouts, which is the lesson, does not move.

Self-studyWhy "free DDL" is a habit, not a footnote1 min▶

Because CREATE TABLE and ALTER TABLE ADD PARTITION cost nothing, the cheap move is always to describe the data properly before querying it: a table over the curated Parquet, partitions registered or projected as in session 3. Querying raw CSV because "the table already exists" is paying a scanning bill to avoid a free statement.

Real world

The query someone cancelled after a coffee. An analyst starts a broad query against the raw zone, sees it is taking a while, gets a coffee, and cancels it on the way back. The query returned nothing, and the next month's line item still shows the bytes it read before the cancel landed. Nothing went wrong; the pricing page says exactly this. The habit that fixes it is to test a query's shape against one partition first. The scenario is constructed; the billing rule is quoted from the Athena pricing page.

Part 2 · covers three layouts on three questions

Same answer, very different byte counts

6 min live

Three questions, chosen because they pull in different directions. Q2 asks the whole month for two columns. Q3 asks one day for one column. Q4 asks one week for one column. Each is asked of the CSV, the single Parquet file and the copy partitioned by pickup day, and each count below is printed by the build-along script. The CSV has no columns to skip and no folders to prune, so it reads 10,095,345 bytes every time. The other two layouts trade places depending on the question.

LiveWhy the sample bill is flat, and what it looks like at scale3 min▶

On the sample every query costs $0.000048, because the largest read, the whole CSV, is still under the 10 MB minimum. So the sample proves bytes, not dollars. To see dollars, scale the measured shares to a lake where the CSV is 1,024 GB and the team runs each query 100 times a day. That is a modelled calculation, linear in the measured shares, at $5.00 per TB (us-east-1, AWS Price List, 3 October 2026; re-verify before relying on it):

  • Q2, whole month, two columns. CSV $15,000 a month; one Parquet file $293; partitioned $566.
  • Q3, one day, one column. CSV $15,000; Parquet $1,222; partitioned $13.
  • Q4, one week, one column. CSV $15,000; Parquet $1,130; partitioned $88. The script prints the scan: 6.0 GB instead of a terabyte.

Scaling linearly overstates the partitioned layout's losses: at a terabyte a day of trips is millions of rows, and 31 footers become a rounding error next to the data. Read the Q2 row as the direction of the effect, not its size. Your numbers will differ with your own data, columns and query mix.

LiveThe answers do not change1 min▶

Layout is a pricing decision, never a correctness one. On every layout, payment type 1 has an average tip of 4.1507 across 78,236 trips (Q2); 15 January has 2,591 trips with fares of $50,935.89 (Q3); and the busiest pickup zones for 15 to 21 January are 161 with 1,088 pickups, 132 with 1,086 and 237 with 1,085 (Q4). The build-along prints the Q2 answer from the partitioned copy so you can check one yourself. If a layout change ever changes an answer, something other than the layout changed.

Self-studyWhere partitioning loses2 min▶

Q2 asks every day, so the partitioned layout opens all 31 files, and each file brings its own footer and metadata. It reads 381,251 bytes against 197,417 for the single file: nearly twice as much for the same two columns. Session 1 measured the same effect on a whole-month, every-column read (3,023,334 against 2,387,037). Athena's tuning guide warns about the shape: "Having too many partition keys can result in fragmented datasets with too many files and files that are too small." Partition on the column your expensive questions filter on, and check the questions that do not filter on it before you celebrate.

Real world

The dashboard that never asked for a day. A team partitions its trips table by day because the daily operations report filters on the day, and that report gets cheaper overnight. A finance dashboard on the same table only ever asks month-to-date totals, so it opens every day's file on every refresh and reads more than it did before. Both outcomes are the same mechanism, measured above as Q3 and Q2. The scenario is constructed; your numbers will differ.

Part 3 · covers how the bytes are counted, and the limits of a stand-in

Count bytes the way a columnar engine fetches them

4 min live

Every Parquet file ends in a footer that lists each column chunk and its compressed size. A columnar engine reads that footer, then fetches only the chunks the query needs; Athena's documentation says "Only the columns needed for the query are loaded". So the bytes a query costs can be counted from the file alone: the file's overhead (its size minus all its column chunks) plus the chunks the query names. DuckDB's parquet_metadata() exposes exactly those numbers. One detail decides Q3 and Q4: a filter is a column too.

LiveA filter is a column you pay for2 min▶

Q3 asks only for fare_amount, but to know which rows belong to 15 January, an engine reading the single file must also fetch tpep_pickup_datetime. That is why the script adds the time column to the single-file count whenever the question names days, and why Q3 reads 822,585 bytes there. In the partitioned layout the day is in the key, pickup_date=2024-01-15/, registered as the partition key in session 3. The engine picks the folder, opens one file, and fetches one chunk plus that file's footer: 8,968 bytes. Athena's partitioning page says it directly: "If you query a partitioned table and specify the partition in the WHERE clause, Athena scans the data only from that partition."

Self-studyPredicate pushdown, and why our single-file numbers are an upper bound2 min▶

Athena's columnar storage page adds a second skip: "Predicate pushdown in Parquet and ORC enables Athena queries to fetch only the blocks it needs, improving query performance." Parquet keeps statistics such as minimum and maximum values per row group, so on a large file sorted by time an engine may skip whole row groups that cannot contain 15 January. Our files are each a single row group, far below the 128 MB row group default the guide mentions, so there is nothing to skip inside them, and the script counts the full chunks. On large production files Athena may read less than this method predicts for a filtered question on one file. Treat the single-file Q3 and Q4 counts as what you pay without that help, and the console as the final word.

Self-studyWhy DuckDB is a stand-in, not a meter1 min▶

DuckDB answers the questions so you can see the answers match across layouts. It does not measure what Athena would bill, and the script never asks it to: the byte counts come from file sizes on disk and the column chunk sizes in each footer. That separation is deliberate. A local engine has its own caching and reading strategy; the file's own metadata is the same whichever engine reads it. If you run these queries on a real account, compare each with Athena's "Data scanned" figure; where they differ, the console is the bill. File-format internals (row groups, encodings, statistics) are taught in learn-ai-infra; here they matter only as bytes.

Real world

Ten rows every morning. An analyst starts each day with SELECT * FROM raw_trips LIMIT 10 on the raw CSV table, to "just look at the data". It feels free because it returns ten rows. But Athena bills bytes scanned, not rows returned, and a CSV has no column chunks to skip and no footer to consult: whatever the engine reads to find those rows is what is billed. How far Athena reads before a LIMIT stops it is engine behaviour these pages have not measured, so do not count on LIMIT to make it cheap; check "Data scanned" in the console for your table. The cheaper habit is to preview from the curated Parquet, name the columns, and filter on the partition. The scenario is constructed.

Build-along

Bytes per question, measured from the files

★ 22 min · everyone builds

One Python file, about fifty lines, a few seconds to run. It reads the three layouts session 1 wrote, counts the bytes each question needs from each layout, prices each count with Athena's rule, and asks DuckDB for one answer as a check. The output below is pasted from a real run of exactly this code. Predict the cheapest layout for each question before you run it.

Reuse the environment and the out/ folder from analyst session 1. Same folder, same .venv, same pinned versions; nothing new to install. This script reads out/trips.csv, out/trips.parquet and out/partitioned/. If they are missing, run analyst session 1's script first.

★ Step 1 · setup (verified 3 October 2026). .venv/bin/activate python -c "import duckdb; print(duckdb.__version__)" # expect 1.5.6 ls out/trips.csv out/trips.parquet && ls out/partitioned | wc -l # expect 31

Two measuring helpers. file_overhead is the file's size minus all its column chunks: footer, schema, headers. col_bytes sums the compressed chunks of the columns a query names. Both read only the footer, never the data.

★ Step 2 · b4_athena.py, part 1# Analyst session 4 - Athena bills bytes scanned. DuckDB stands in for the engine; the bytes are the files'. import math, os import duckdb MB, TB, USD_PER_TB = 2 ** 20, 2 ** 40, 5.00 # us-east-1, AWS Price List, retrieved 2026-10-03 con = duckdb.connect() def file_overhead(path): cols = con.execute(f"SELECT SUM(total_compressed_size) FROM parquet_metadata('{path}')").fetchone()[0] return os.path.getsize(path) - cols def col_bytes(path, cols): q = ",".join(f"'{c}'" for c in cols) return con.execute(f"SELECT COALESCE(SUM(total_compressed_size),0) FROM parquet_metadata('{path}') WHERE path_in_schema IN ({q})").fetchone()[0]

Count per layout, then price it. The CSV is read whole. The single Parquet file pays its overhead, the named columns, and the pickup time column when the question filters on days. The partitioned layout skips folders outside the day range, then pays overhead plus named columns for each file it opens. bill is Athena's rule from Part 1, line for line.

★ Step 3 · b4_athena.py, part 2def scanned(layout, cols, days=None): if layout == "csv": return os.path.getsize("out/trips.csv") if layout == "parquet": need = cols + (["tpep_pickup_datetime"] if days else []) return file_overhead("out/trips.parquet") + col_bytes("out/trips.parquet", need) total = 0 for d in sorted(os.listdir("out/partitioned")): day = d.split("=")[1] if days and not (days[0] <= day <= days[1]): continue for f in os.listdir(f"out/partitioned/{d}"): p = f"out/partitioned/{d}/{f}" total += file_overhead(p) + col_bytes(p, cols) return total def bill(b): mb = max(10, math.ceil(b / MB)) return mb * MB / TB * USD_PER_TB

Ask the three questions of the three layouts, then check one answer. The last query reads the partitioned copy with DuckDB, so you can confirm it gives the same Q2 answer quoted in Part 2.

★ Step 4 · b4_athena.py, part 3Q = [("Q2 avg tip by payment type, month", ["payment_type", "tip_amount"], None), ("Q3 fares on 15 January", ["fare_amount"], ("2024-01-15", "2024-01-15")), ("Q4 pickups per zone, 15-21 January", ["PULocationID"], ("2024-01-15", "2024-01-21"))] csv = os.path.getsize("out/trips.csv") for name, cols, days in Q: print(name) for layout in ("csv", "parquet", "partitioned"): b = scanned(layout, cols, days) print(f" {layout:11s} {b:>10,d} bytes {b / csv:7.2%} of the CSV billed ${bill(b):.6f}") print("at 1 TB of CSV, Q4 partitioned would scan", f"{scanned('partitioned', ['PULocationID'], ('2024-01-15','2024-01-21')) / csv * 1024:.1f}", "GB") ans = con.execute("""SELECT payment_type, ROUND(AVG(tip_amount),4), COUNT(*) FROM read_parquet('out/partitioned/*/*.parquet', hive_partitioning=true) GROUP BY 1 ORDER BY 1""").fetchall() print("Q2 answer (partitioned):", ans)

Check yourself

Three questions

Clear all three and analyst session 4 gets stamped in your passport.

1 · On the 100,000-row sample, Q2 reads 10,095,345 bytes from the CSV and 197,417 from the Parquet file, yet both are billed $0.000048. Why?

Bytes are rounded up to the megabyte with a 10 MB minimum. Every sample query sits under the floor, so the sample proves bytes, not dollars; the difference shows up only at scale.

2 · For Q2, a whole-month question, the partitioned layout reads 381,251 bytes and the single Parquet file 197,417. What explains it?

Partitions only pay when the question filters on the partition column. Otherwise you pay for every file's overhead, which is why the same layout wins Q3 and Q4 and loses Q2.

3 · A table is stored as Snappy-compressed Parquet. Which bytes does Athena bill a query for?

The tuning guide says "you pay for the number of bytes scanned before decompression". Compression is a direct discount, and column pruning means only the chunks a query names are read.
