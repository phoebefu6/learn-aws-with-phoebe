Part 1 · covers databases, tables and what the catalog stores

The catalog holds the description, S3 holds the bytes

5 min live

The AWS Glue Developer Guide puts it in one line: the Data Catalog "is a centralized repository that stores metadata about your organization's data sets", and "It acts as an index to the location, schema, and runtime metrics of your data sources." Not one byte of trip data moves into it. A table entry is a few hundred bytes of JSON: column names and types, a Location in S3, the file format, and the partition keys. Engines read that entry first and then go to S3 for exactly the files it points at. A prefix the catalog does not describe is, as far as SQL is concerned, not there.

LiveDatabases, tables, and who reads them3 min▶

The guide says the metadata "is organized into databases and tables, similar to a traditional relational database catalog." A database here is just a namespace, lake; it owns no storage and no compute. A table is the entry in the figure. The same guide lists the readers: the catalog "seamlessly integrates with other AWS services, such as AWS Lake Formation, Amazon Athena, Amazon Redshift Spectrum, and Amazon EMR." That is the practical point. Register a table once and four engines see the same columns, the same types and the same files. Register it twice under two names and they see two tables that will drift apart.

Lake Formation's own permission model sits on top of these tables; these pages do not teach it, and the access-control concepts behind it live in learn-data-access-control.

Self-studyWhat is inside a table entry2 min▶

The build-along writes every field by hand, so read them once. Columns is the list of names and types. Location is the S3 prefix the files live under. InputFormat, OutputFormat and SerdeInfo tell an engine how to read the bytes, here the Hive Parquet classes. PartitionKeys names the columns that live in the folder names rather than inside the files, which is why session 1 wrote pickup_date into the key and left it out of the Parquet data. TableType EXTERNAL_TABLE says the data lives outside the catalog. Each partition entry then carries its own Location, one per day prefix.

Real world

Two tables, one set of files. The finance analysts register curated/orders/ as fin.orders; a quarter later the growth team, not finding it, crawls the same prefix into growth.orders_raw. Both point at the same bytes. Then finance changes a column type in its entry, growth's crawler infers a different one, and the two teams' revenue numbers stop agreeing while reading identical files. The repair is not technical: one owner per table, and everyone else reads that entry. The scenario is constructed; the mechanism is the one in the figure.

Part 2 · covers partitions in the catalog, crawlers and partition projection

A partition the catalog does not list is a partition no query reads

6 min live

Session 1 split the trips into 31 day prefixes. The prefixes alone do nothing for SQL. What makes pruning possible is the catalog's partition list: for each value of pickup_date, a Location. A query that filters on pickup_date asks the catalog which partitions match, and reads only those prefixes. The build-along registers all 31; a question about 15 to 21 January matches 7 of them. The Well-Architected Data Analytics Lens names the payoff of partitioning in BP 10.4: "a full table scan is avoided".

LiveCrawler or explicit registration3 min▶

There are two ways the partition list gets filled. A crawler: "You can populate the Data Catalog using a crawler, which automatically scans your data sources and extracts metadata." It infers columns, types and partitions from what it finds, which is fast to set up and right most of the time. Explicit registration: you write the table and its partitions yourself, as the build-along does with create_table and batch_create_partition, or as DDL in Athena. Explicit is slower to write and easy to review: the schema is a file in version control, a changed type shows up in a diff, and nothing changes unless someone merges it. A crawler's guess changes when the data changes.

Either way, the ingest job that writes a new day's files must also make sure that day is registered, or the new files sit in S3 unread. Scheduling that pairing belongs to learn-data-orchestration; the pipelines themselves to learn-data-engineering.

Self-studyPartition projection, and its one-engine catch2 min▶

For a key as regular as a date, listing every partition is busywork. Athena offers another way, from the Athena User Guide: "In partition projection, Athena calculates partition values and locations using the table properties that you configure directly on your table in AWS Glue." No partition entries are stored; Athena works them out from a rule. The catch is in the next sentence of the same page: "Partition projection is usable only when the table is queried through Athena." Redshift Spectrum or EMR reading that same table do not get the projected partitions. If more than one engine reads the table, register the partitions.

Self-studyOne catalog, as a governance decision1 min▶

The Data Analytics Lens, BP 7.1: "Building a central Data Catalog to store, share, and manage metadata across the organization is an integral part of data governance." The reasoning is the Part 1 story in reverse: one entry per dataset means one definition of every column. Treat the lens with its date in mind; its last major update was published December 22, 2023, almost three years ago.

Real world

The day that was never there. An ingest job is rewritten and the new version forgets the step that registers each day's partition. The files keep landing in S3 on time. The dashboard keeps refreshing, without error, and every day since the rewrite is simply missing from it, because the table's partition list stopped growing. Nobody notices until month-end totals come in low. The scenario is constructed; the mechanism is the one in the figure: unregistered is unread.

Part 3 · covers catalog prices and schema drift

The catalog is cheap; a stale schema is not

4 min live

Glue's prices are small enough to ignore and worth knowing anyway (us-east-1, AWS Price List, 3 October 2026; prices change, so re-verify before relying on them): Data Catalog storage is $1 per 100,000 objects a month beyond the free tier, which is $0.00001 per object; requests are $1 per million; a crawler runs at $0.44 per DPU-hour. The expensive failure is not the bill. It is a schema that no longer matches the files. The guide says the catalog "automatically captures and manages the schema of your data sources, including schema inference, evolution, and versioning." Versioning means the old schema is kept when a new one is recorded. It does not mean anyone reads the difference.

LiveRead the types the script registered2 min▶

The build-along's real output prints the first three columns as the catalog stored them: ('vendorid', 'int'), ('tpep_pickup_datetime', 'timestamp'), ('tpep_dropoff_datetime', 'timestamp'). Two things to notice. The timestamps are timestamps, not strings, because the types came from the Parquet file through DuckDB's DESCRIBE, so a date filter compares dates rather than text. And the TLC's own column is spelled VendorID; the script lower-cases every name, following the Hive and Glue convention of lower-case column names, so that SQL written against the table never depends on the capitalisation an upstream system happened to choose. That is one small schema decision made on purpose. A crawler would have made it for you, its way.

Self-studyWhat the catalog costs at scale2 min▶

A modelled example, your numbers will differ: 100 tables, each partitioned by day and kept for a year, is 36,500 partition entries. Beyond the free tier, at $0.00001 per object, that is about $0.37 a month. A million catalog requests, every engine asking for partition lists all month, is $1. The free tier's size is on AWS's Glue pricing page; these pages do not quote it, so check it there. The one Glue line that can grow is the crawler, billed at $0.44 per DPU-hour (us-east-1, AWS Price List, 3 October 2026; re-verify before relying on it): how many DPU-hours a crawl takes depends on how many files it has to open, so a crawler pointed at a small-files table from session 1's warning is a crawler that runs long.

Real world

Renamed on a Friday. The source team renames tip_amount to tip in their export, a tidy change on their side. The weekend crawler records a new schema version. On Monday the tips dashboard errors, and the finance extract that selected columns by position quietly fills a field with the wrong numbers. The schema history shows exactly when it changed; nobody was watching it. The usual repair is a contract: the producer announces schema changes, and the table is registered explicitly so a rename has to pass review. The scenario is constructed; the versioning it relies on is the documented one.

Build-along

Register the lake in a catalog on your laptop

★ 22 min · everyone builds

Five steps, one Python file, a few seconds of run time. The script reads the schema from the sample file, creates a database and a table in a mocked Glue Data Catalog, registers one partition per pickup day, and asks the catalog which partitions a one-week question needs. The output below is pasted from a real run of exactly this code.

Reuse the environment and the sample from analyst session 1. Same folder, same .venv, same pinned versions; nothing new to install. The script reads yellow_tripdata_2024-01_sample.parquet from the current folder, so run it where session 1 downloaded it. If you are starting fresh, run analyst session 1's step 1 first.

★ Step 1 · setup (verified 3 October 2026). .venv/bin/activate ls yellow_tripdata_2024-01_sample.parquet # 2,776,217 bytes python -c "import moto, boto3, duckdb; print(moto.__version__, boto3.__version__, duckdb.__version__)" # expect 5.2.3 1.43.108 1.5.6

Read the schema from the file, not from memory. DuckDB's DESCRIBE returns each column's name and type without reading the data. A small map turns DuckDB types into the Hive type names the catalog uses, and every name is lower-cased. The last line lists the distinct pickup days, which become the partitions.

★ Step 2 · b3_catalog.py, part 1# Analyst session 3 - the Glue Data Catalog, run locally against moto import os, boto3, duckdb from moto import mock_aws os.environ.setdefault("AWS_DEFAULT_REGION", "us-east-1") SAMPLE = "yellow_tripdata_2024-01_sample.parquet" con = duckdb.connect() schema = con.execute(f"DESCRIBE SELECT * FROM '{SAMPLE}'").fetchall() TYPES = {"INTEGER": "int", "BIGINT": "bigint", "DOUBLE": "double", "VARCHAR": "string", "TIMESTAMP": "timestamp"} columns = [{"Name": n.lower(), "Type": TYPES[t]} for n, t, *_ in schema] days = [r[0] for r in con.execute(f"SELECT DISTINCT CAST(tpep_pickup_datetime AS DATE)::VARCHAR FROM '{SAMPLE}' ORDER BY 1").fetchall()]

Create the database and the table. This is the entry from Part 1, field by field: the columns, the Location under curated/nyc_taxi/, the Parquet reader classes, and pickup_date as a partition key of type date. Nothing here touches S3; the catalog only stores the pointer.

★ Step 3 · b3_catalog.py, part 2with mock_aws(): glue = boto3.client("glue") glue.create_database(DatabaseInput={"Name": "lake"}) glue.create_table(DatabaseName="lake", TableInput={ "Name": "nyc_taxi", "StorageDescriptor": { "Columns": columns, "Location": "s3://acme-lake/curated/nyc_taxi/", "InputFormat": "org.apache.hadoop.hive.ql.io.parquet.MapredParquetInputFormat", "OutputFormat": "org.apache.hadoop.hive.ql.io.parquet.MapredParquetOutputFormat", "SerdeInfo": {"SerializationLibrary": "org.apache.hadoop.hive.ql.io.parquet.serde.ParquetHiveSerDe"}, }, "PartitionKeys": [{"Name": "pickup_date", "Type": "date"}], "TableType": "EXTERNAL_TABLE", "Parameters": {"classification": "parquet"}, })

Register one partition per day, then ask the catalog. batch_create_partition writes all 31 entries in one call, each with its own day prefix. get_table and get_partitions read them back the way an engine would, and the last line does the pruning by hand: which partition values fall in 15 to 21 January.

★ Step 4 · b3_catalog.py, part 3 glue.batch_create_partition(DatabaseName="lake", TableName="nyc_taxi", PartitionInputList=[ {"Values": [d], "StorageDescriptor": {"Location": f"s3://acme-lake/curated/nyc_taxi/pickup_date={d}/"}} for d in days]) t = glue.get_table(DatabaseName="lake", Name="nyc_taxi")["Table"] print("table:", t["DatabaseName"] + "." + t["Name"], "|", len(t["StorageDescriptor"]["Columns"]), "columns |", "partition key:", t["PartitionKeys"][0]["Name"], "|", t["StorageDescriptor"]["Location"]) print("first three columns:", [(c["Name"], c["Type"]) for c in t["StorageDescriptor"]["Columns"][:3]]) parts = glue.get_partitions(DatabaseName="lake", TableName="nyc_taxi")["Partitions"] print("partitions registered:", len(parts), "| first:", parts[0]["StorageDescriptor"]["Location"] if parts else None) week = [p for p in parts if "2024-01-15" <= p["Values"][0] <= "2024-01-21"] print("a query on 15-21 January needs", len(week), "of", len(parts), "partitions")

Run it and compare with this real output. Look at line 2: vendorid, lower-case, although the TLC file spells it VendorID. That is the script's n.lower() applying the Hive and Glue lower-case convention, and it is the name every query in session 4 uses. moto is a mock: it stores what you send and answers the API, but it is not AWS's catalog, so treat the output as proof of the calls, not of how a real engine plans a query.

Check yourself

Three questions

Clear all three and analyst session 3 gets stamped in your passport.

1 · After the build-along, what does the catalog hold for lake.nyc_taxi?

The guide calls the catalog "an index to the location, schema, and runtime metrics" of your data. It describes the files and points at them; engines then read S3 directly.

2 · Files for 22 January land in curated/nyc_taxi/pickup_date=2024-01-22/, but nobody registers the partition. What does a query for that day return?

With registered partitions, the partition list is what the engine prunes against. Unregistered is unread, and it fails silently, which is why the ingest job and the registration step belong together.

3 · A table uses partition projection instead of registered partitions. Redshift Spectrum queries it too. What happens?

Athena calculates partition values and locations from the table properties at query time; nothing is stored for other engines to read. A table read by more than one engine needs registered partitions.
