Part 1 · covers principals, credentials and where policies live

Who asks, and where the rules hang

5 min live

A request to AWS has three parts: a principal, the who; an action, such as s3:GetObject; and a resource, such as one object in one bucket. The principal is the account root user, an IAM user, or a role that a person or a job assumes for a while. The rules that answer the request are JSON policies, and they hang in one of two places: on the principal (identity-based) or on the thing being asked for (resource-based, such as a bucket policy).

LiveRoot, users, roles: three ways to be "who"2 min▶

The root user is the identity that opened the account. AWS's evaluation page says it plainly: "By default, all requests are implicitly denied with the exception of the AWS account root user, which has full access." No policy you write narrows it inside its own account, which is why the norm is to protect it with MFA and then not use it for daily work.

An IAM user is a named identity that can hold a long-term access key: a key ID and secret that work until somebody revokes them. A role has no long-term key at all. A person or a job assumes it and receives temporary credentials that expire. AWS's best practices are direct about the preference: "Require your human users to use temporary credentials when accessing AWS", and for workloads, "Require workloads to use temporary credentials with IAM roles to access AWS". Where a long-term key is unavoidable, the same page adds "Where possible, we recommend relying on temporary credentials instead of creating long-term credentials such as access keys."

On MFA, the guidance is "for scenarios in which you need an IAM user or root user in your account, require MFA for additional security", and on which kind: "We recommend that you use phishing-resistant MFA such as passkeys and security keys wherever possible."

LiveOne policy, read line by line2 min▶

A policy is a list of statements. Each statement has an Effect (Allow or Deny), an Action (what may be done, as service:Name), a Resource (to which ARN), and optionally a Condition (only when the request looks like this). Here is part of the analyst policy that analyst session 8's evaluator uses, trimmed to two statements:

★ An identity-based policy, readable{ "Version": "2012-10-17", "Statement": [ { "Sid": "ReadCurated", "Effect": "Allow", "Action": ["s3:GetObject", "s3:ListBucket"], "Resource": ["arn:aws:s3:::acme-lake", "arn:aws:s3:::acme-lake/curated/*"] }, { "Sid": "DenyHttp", "Effect": "Deny", "Action": "s3:*", "Resource": ["arn:aws:s3:::acme-lake", "arn:aws:s3:::acme-lake/*"], "Condition": {"Bool": {"aws:SecureTransport": "false"}} } ] }

Read it aloud as a leader would: the analyst may list the lake and read anything under curated/; nobody holding this policy may touch the lake over plain HTTP. Two details matter in reviews. Action names are forgiving: "The prefix and the action name are case insensitive". Resource names are not: "In the Resource element, the IAM user name is case sensitive." And the bucket ARN is not its objects: acme-lake names the bucket, acme-lake/* names what is inside.

Self-studyIdentity-based versus bucket policies2 min▶

An identity-based policy travels with the principal: whatever bucket the analyst asks, the same policy is read. A bucket policy stays with the bucket and must say who it applies to, with a Principal element. Within one account the two add up: AWS describes the result as a union, so either one allowing is enough. One sentence from the enforcement page surprises most reviewers: resource-based policies that grant permissions to an IAM user ARN "are not limited by an implicit deny in an identity-based policy or permissions boundary." A generous bucket policy can therefore open a door that the user's own policy never mentions. When you review a lake's access, read the bucket policy as carefully as the role policies.

Cross-account access, role sessions and session policies change these rules and are not taught on these pages; AWS's "Policy evaluation logic" page is the place to go next.

Real world

The key that lived in a notebook. An analyst needs data from the lake for a weekend analysis. The quickest path is an IAM user with an access key, pasted into the first cell of a notebook. The notebook goes into a repository, the repository is made public for a conference talk, and the key is still valid, because a long-term key works until someone revokes it and nobody owned that job. A role assumed through the company's single sign-on would have handed out credentials that expired on their own. The story is constructed, a composite of a pattern AWS's best practices are written against.

Part 2 · covers how AWS decides: implicit deny, explicit Deny, the evaluation order

Six gates, and the first one that decides

6 min live

AWS starts every request at no. "By default, all requests are implicitly denied", root excepted. Then it looks in every applicable policy for an explicit Deny, because "An explicit deny overrides an explicit allow." Only after that does it look for something that allows the request, gate by gate. The order below keeps the same scope as analyst session 8: one IAM user in one account.

LiveImplicit deny and explicit Deny are not the same no2 min▶

An implicit deny is silence: no policy said yes. It is the starting state of every request, and any Allow that applies can lift it. An explicit Deny is a statement with "Effect": "Deny" that matches the request. It is checked first, in every applicable policy at once, and the enforcement page is unambiguous: "If the enforcement code finds even one explicit deny that applies", the final decision is Deny. No Allow anywhere overturns it.

That difference is the leader's lever. Allows are how you grant work; explicit Denies are how you set a floor that survives the next person's generous Allow. A Deny on deleting the lake bucket stays true when someone later attaches a wide policy to the same role, which is exactly what Part 3 measures.

LiveWalking the six gates2 min▶

Gate 1: any explicit Deny in an SCP, the bucket policy, an identity policy or a boundary ends the walk. Gate 2: if a service control policy applies and nothing in it allows the request, Deny. Gate 3: if the bucket policy names this user's ARN and allows, Allow, for the reason in Part 1. Gate 4: if no identity-based policy allows, implicit Deny. Gate 5: if a permissions boundary is set and does not allow, Deny. Gate 6: anything still walking is allowed.

AWS's full order has two more stops this scope leaves out: resource control policies, and session policies for role sessions. They change verdicts, so the evaluator in analyst session 8 refuses to guess about them rather than quietly skipping them. The full page is "How AWS enforcement code logic evaluates requests to allow or deny access".

Self-studyUnion, intersection, ceiling2 min▶

Three words cover how policies combine in one account. Identity-based plus resource-based is a union: either may grant. Identity-based plus a permissions boundary is an intersection: the boundary never grants anything on its own, it only limits what the identity policy can reach, which is why it suits delegating role creation to a team without handing them the keys to everything. Identity-based plus an SCP must both allow: the SCP is the ceiling set by the organisation, and no policy inside the account can reach above it.

Conditions follow their own small rules worth knowing before a review. If a key named in a condition is missing from the request, "the values do not match and the condition is false", and a negated operator turns true. Several operators in one block are ANDed; several values for one key are ORed. The Organizations side of SCPs, and account design generally, is not taught on these pages.

Real world

The Allow that did nothing. A data engineer cannot delete an old staging bucket. They add s3:* to their own role, then "Action": "*", and the error does not change. Two hours later someone finds the cause: an explicit Deny on s3:DeleteBucket in an SCP set by the platform team a year earlier. Every added Allow was read at a gate the request never reached. The guardrail worked exactly as designed; what was missing was a note saying it existed and who owned it. Constructed, from a common pattern.

Part 3 · covers what one wildcard hands over, measured

One wildcard, counted

4 min live

Analyst session 8 runs a policy evaluator, written in JavaScript and ported to Python, that follows the IAM documentation sentence by sentence; on all 192 verdicts it computes, the two agree. It holds an analyst role with two policies: read the curated zone, run Athena, write query results; and guardrails that deny plain HTTP on the lake and deny deleting the bucket or changing its policy. Then it adds one statement, an Allow of "Action": "*" on "Resource": "*", and counts.

LiveRead the two numbers2 min▶

Before the wildcard, the analyst can do 7 of 24 data-team actions: read and list curated data, write query results, run Athena and read its results, read the table and its partitions in the Glue catalog. After one added statement, 22 of 24. The fifteen new ones include reading the raw zone, overwriting curated files, deleting objects, creating IAM users and access keys, changing Lambda code, starting EC2 instances and decrypting with a KMS key. The demo request in analyst session 8, s3:PutObject into curated/, goes from implicit Deny to Allow.

Only s3:DeleteBucket and s3:PutBucketPolicy stay denied, because the guardrail policy denies them explicitly and gate 1 runs before any Allow is read. Across the full table of 36 test cases, each tied to a documentation sentence, allowed requests go from 16 to 28 of 36, and only 24 of 36 still match the verdicts the documentation predicts: 12 implicit denies became allows. These are measured counts from the evaluator, and the full bench, with its two "break the logic" buttons, is in analyst session 8.

LiveGuardrail Denies are the floor1 min▶

The lesson is not "never write a wildcard". People will, under deadline, and some service integrations ask for wide grants. The lesson is to decide in advance which few actions must never happen to the lake, and to deny them explicitly, in a place the people writing Allows do not own: a separate guardrail policy, a boundary, or an SCP. Then the worst mistake a generous Allow can make is bounded by a floor you chose calmly.

One variant deserves a separate warning. NotAction with Allow reads like a restriction and behaves like a grant. AWS's example "allows users to access every action in every AWS service except for IAM", and the same page cautions that it "could result in granting users more permissions than you intended."

Self-studyGetting back to least privilege with Access Analyzer2 min▶

AWS's first best practice is "grant only the permissions required to perform a task". The hard part is knowing which permissions a role actually needs. The best-practices page points at a tool for that: "Use IAM Access Analyzer to generate least-privilege policies based on access activity". In AWS's words, "IAM Access Analyzer analyzes the services and actions that your IAM roles use, and then generates a fine-grained policy that you can use." For a leader the practical move is a habit: when a role carries a wildcard, ask for the generated policy from real activity and compare the two. The process questions, who reviews, how often, and against which design, belong to learn data access control.

Real world

Admin for the demo. A Friday demo fails on an access error. The fastest fix is one statement, "Action": "*", on the demo role. The demo works, the statement stays, and six months later the role is still the one the reporting job uses, with permission to create IAM users. Nothing was breached; the team simply carried twenty-two doors open where seven were needed. The two that stayed shut were the two somebody had denied explicitly. Constructed; the 7 and 22 come from the evaluator.

Build-along

The access matrix, on paper

★ 22 min · everyone builds

No console and no account. Three roles down the side, five zones across the top, and in every cell one of three marks: Allow, Deny, or nothing. "Nothing" is not a gap in the sheet; it is an implicit deny, and most cells should say it. Then pick the two actions that get an explicit Deny for everyone. The worked examples below are constructed; your zones and roles will differ.

Draw the grid. Rows: analyst, data engineer, ingest job. Columns: raw (data as it arrived), curated (cleaned Parquet), results (where query output lands), catalog (the Glue tables), and IAM itself. If your lake has a different zone, such as a sandbox, add a column; keep IAM as the last one, because who can change permissions is a permission too.

Fill the analyst row. Start every cell at "nothing" and only write Allow where the job cannot be done without it. Write the verb, not the service name.

★ Worked example: the analyst row (constructed)Raw: nothing (reads curated only; raw may hold unmasked fields) Curated: Allow read, list Results: Allow write (Athena needs somewhere to put query output) Catalog: Allow read (table, database, partitions) IAM: nothing Credentials: a role through single sign-on, never an access key

Fill the ingest job row. A job is a principal too, and the best practice for workloads is a role with temporary credentials. Ask what the job writes, and what it never needs to read.

★ Worked example: the ingest job row (constructed)Raw: Allow write (lands files as they arrive) Curated: Allow write (writes the cleaned Parquet) Results: nothing Catalog: Allow add partitions IAM: nothing Credentials: a role assumed by the job; no key stored in its code

Fill the data engineer row yourself. This is the row that drifts toward "everything", because engineers fix things. Write down which cells truly need Allow day to day, and which are break-glass work that should go through a separate, logged role. Expect at least one argument; it is the useful part of the exercise.

Choose the two explicit Denies. Pick the two actions whose single occurrence would hurt most, and deny them for every role in the matrix, in a policy none of the three roles' owners can edit. Gate 1 then protects them whatever Allow is added later.

★ Worked example: the floor (same as the analyst session 8 bench)Deny s3:DeleteBucket on the lake (nobody deletes the lake) Deny s3:PutBucketPolicy on the lake (nobody rewrites who can reach it) Where: a guardrail policy, a boundary or an SCP owned by the platform lead Bonus: Deny s3:* on the lake when aws:SecureTransport is "false"
✗ The matrix that grants by defaultanalyst: s3:* on the lake "to save tickets" data engineer: "Action": "*" until the migration is done ingest job: an IAM user with an access key in the pipeline config guardrails: none, everyone is careful

Count the "nothing" cells. In a healthy matrix most cells are empty. If a reviewer sees more Allows than blanks, the question to ask is not "is anyone misusing this?" but "which of these would we write today if we started from no?". AWS already starts from no; the matrix should too.

Check yourself

Three questions

Clear all three and leader session 3 gets stamped in your passport.

1 · A role has an Allow of "Action": "*" on "Resource": "*", and a guardrail policy with an explicit Deny on s3:DeleteBucket. Someone using the role tries to delete the lake bucket. What happens?

"An explicit deny overrides an explicit allow." In the analyst session 8 evaluator, the wildcard lifted the analyst from 7 to 22 of 24 actions, and DeleteBucket and PutBucketPolicy still held for exactly this reason.

2 · A new IAM user has no policies attached at all and asks to read an object in the lake. What does "implicitly denied" mean for that request?

"By default, all requests are implicitly denied", root excepted. Implicit deny is silence, and an Allow can lift it. An explicit Deny is a statement, and nothing lifts that.

3 · Why do AWS's best practices prefer a role for a nightly ingest job over an IAM user with an access key?

"Require workloads to use temporary credentials with IAM roles to access AWS", and "Where possible, we recommend relying on temporary credentials instead of creating long-term credentials such as access keys." A leaked key is only as dangerous as it is long-lived.
