S3 layout and Parquet

Before anyone writes a query, somebody decides how the files sit in S3: what the keys look like, which format the bytes are in, and whether the data is split by date. Those three decisions set the price of every query for years. Tonight we take 100,000 real New York taxi trips, write them three ways, upload them to an S3 bucket that runs on your laptop, and measure exactly how many bytes a question has to read in each.

Part 1 · covers buckets, keys and prefixes

There are no folders, only keys

5 min live

S3 stores objects in buckets. Each object has a key, a string such as curated/nyc_taxi/pickup_date=2024-01-15/data_0.parquet. The console draws folders, but the slashes are just characters in the key; a "folder" is a prefix that many keys share. That sounds like trivia until you learn that engines prune by prefix, that throughput is counted per prefix, and that lifecycle rules and IAM policies are written against prefixes too.

LiveRaw, curated, and why two zones3 min▶

A common lake layout keeps a raw zone, data exactly as it arrived, and a curated zone, the same data cleaned and stored in a format built for reading. Raw is the receipt: if a transformation turns out to be wrong you can rebuild curated from it. Curated is what analysts and engines read. Because both are prefixes in a bucket, different IAM rules and different lifecycle rules can point at each: analysts read curated only, raw moves to a colder storage class after a while. Session 2 writes that IAM rule as code.

Self-studyThroughput is counted per prefix2 min▶

AWS's performance guidance says an application "can achieve at least 3,500 PUT/COPY/POST/DELETE or 5,500 GET/HEAD requests per second per partitioned Amazon S3 prefix", and that there is no limit to the number of prefixes in a bucket. Spreading hot data across prefixes raises the ceiling; while S3 scales to a new rate you may see 503 "Slow Down" responses. S3 gives "strong read-after-write consistency for PUT and DELETE requests of objects", so a file you just wrote is the file the next read sees.

Part 2 · covers row and columnar formats

CSV is read whole, Parquet is read by column

6 min live

A CSV file stores one row after another. To answer "average tip by payment type", an engine must read every byte of every row, because the two columns it needs are scattered through all of them. Parquet stores each column in its own compressed chunks and keeps a footer that says where each chunk starts. An engine reads the footer, then only the chunks it needs. Athena's documentation names both moves: "Only the columns needed for the query are loaded", and you "pay for the number of bytes scanned before decompression".

LiveThree wins in one format3 min▶

Smaller. The whole Parquet file is 23.6 percent of the CSV, because each column is compressed with an encoding suited to its type. Column pruning. A question that names two columns reads two columns. Typed. A timestamp is stored as a timestamp, not as text an engine must parse on every read. Athena's pricing page puts the combined effect at "up to 90%" saved per query from compressing, partitioning and converting to columnar formats; on this sample the two-column question reads 1.96 percent of the CSV's bytes, a saving of 98 percent, because the question is narrow.

Self-studyWhere the format internals live1 min▶

Row groups, dictionary encoding, page statistics and table formats such as Iceberg are taught properly in the AI infrastructure course's storage session, "Cheap bytes, expensive reads". Here the format matters only as a bill: how many bytes a question forces an engine to read from S3.

Part 3 · covers partitioning, and when it backfires

Partitions skip folders; small files cost footers

4 min live

Partitioning writes the data into one prefix per value of a column, here one per pickup day: pickup_date=2024-01-15/. A query that filters on that column reads only the matching prefixes, and Athena's documentation says so plainly: "Athena scans the data only from that partition". The catch is the same mechanism in reverse. Every partition is its own file with its own footer, and a query that needs every day pays for every footer.

LiveThe small-files trade, in AWS's words2 min▶

Athena's tuning guide is direct: "Datasets that consist of many small files result in poor overall query performance", "loading a single bigger file from Amazon S3 is faster than loading the same records from many smaller files", and "For small files, the overhead of the columnar file format outweighs the benefits". On our sample each daily file is 73,785 to 113,419 bytes, 2,310 to 3,897 trips, far smaller than a single Parquet row group, so the overhead is visible: a whole-month question reads 26.7 percent more bytes from the partitioned layout than from one file. At production sizes a day of trips is millions of rows and the footer becomes a rounding error. The rule is not "always partition"; it is "partition on the filter you actually use, at a grain that keeps files big".

AWS gives no single target file size in the Athena documentation. The figure people quote, 128 MB, is the default Parquet row group size the guide mentions, not a file-size rule.

Real world

Partitioned by the minute. An ingestion job writes one file per minute per source because that is when events arrive. A year later the table holds hundreds of thousands of tiny files, queries spend more time opening files than reading data, and the bill is dominated by footers and request overhead. The usual repair is a compaction job that rewrites each day into a few large files. The scenario is constructed; the mechanism is the one measured above.

Build-along

Three layouts in a bucket on your laptop

★ 22 min · everyone builds

Five steps, one Python file, about two minutes of run time. The outputs below are pasted from a real run of exactly this code. Work in a fresh folder: the later analyst sessions reuse the out/ folder it creates.

Create an environment with the versions this page was verified on, and download the sample. The sample is 2,776,217 bytes: 100,000 rows drawn with seed 20240101 from the TLC's January 2024 yellow taxi file. Run in a new, empty folder.

★ Step 1 · setup (verified 3 October 2026)python3 -m venv .venv && . .venv/bin/activate pip install "moto[s3,iam,glue,awslambda]==5.2.3" boto3==1.43.108 duckdb==1.5.6 pyarrow==25.0.1 curl -O https://phoebefu6.github.io/learn-aws-with-phoebe/data/yellow_tripdata_2024-01_sample.parquet

Write the same rows three ways with DuckDB. One CSV, one Parquet file, and Parquet partitioned by pickup day. A derived pickup_date column becomes the folder name and is not stored inside the files.

★ Step 2 · b1_layout.py, part 1import os, boto3, duckdb from moto import mock_aws SAMPLE = "yellow_tripdata_2024-01_sample.parquet" os.environ.setdefault("AWS_DEFAULT_REGION", "us-east-1") con = duckdb.connect() con.execute("SET threads=1") con.execute(f"CREATE TABLE trips AS SELECT *, CAST(tpep_pickup_datetime AS DATE) AS pickup_date FROM '{SAMPLE}'") os.makedirs("out", exist_ok=True) con.execute("COPY (SELECT * EXCLUDE (pickup_date) FROM trips) TO 'out/trips.csv' (HEADER)") con.execute("COPY (SELECT * EXCLUDE (pickup_date) FROM trips) TO 'out/trips.parquet' (FORMAT parquet, COMPRESSION snappy)") con.execute("COPY trips TO 'out/partitioned' (FORMAT parquet, COMPRESSION snappy, PARTITION_BY (pickup_date), OVERWRITE_OR_IGNORE)")

Upload into a raw and a curated zone of a mocked bucket. Inside mock_aws(), boto3 talks to moto instead of AWS. The keys are the layout decision, written down.

★ Step 3 · b1_layout.py, part 2with mock_aws(): s3 = boto3.client("s3") s3.create_bucket(Bucket="acme-lake") s3.upload_file("out/trips.csv", "acme-lake", "raw/nyc_taxi/2024/01/trips.csv") s3.upload_file("out/trips.parquet", "acme-lake", "curated/nyc_taxi_flat/2024-01.parquet") for root, _, files in os.walk("out/partitioned"): for f in files: part = root.split("partitioned/")[1] # pickup_date=2024-01-15 s3.upload_file(os.path.join(root, f), "acme-lake", f"curated/nyc_taxi/{part}/{f}") pages = s3.get_paginator("list_objects_v2").paginate(Bucket="acme-lake") objs = [o for p in pages for o in p["Contents"]] for prefix in ("raw/", "curated/nyc_taxi_flat/", "curated/nyc_taxi/"): sel = [o for o in objs if o["Key"].startswith(prefix)] print(f"{prefix:24s} {len(sel):3d} objects {sum(o['Size'] for o in sel):>10,d} bytes") print("one partition key:", sorted(o["Key"] for o in objs if "2024-01-15" in o["Key"])[0])

Read the Parquet footer and count what a two-column question needs. DuckDB's parquet_metadata() lists every column chunk and its compressed size, which is what a columnar engine fetches from S3.

★ Step 4 · b1_layout.py, part 3cols = con.execute("""SELECT path_in_schema, SUM(total_compressed_size) FROM parquet_metadata('out/trips.parquet') GROUP BY 1 ORDER BY 2 DESC""").fetchall() need = sum(b for c, b in cols if c in ("payment_type", "tip_amount")) print("parquet column chunks:", len(cols), "| two columns needed:", f"{need:,d}", "bytes of", f"{os.path.getsize('out/trips.parquet'):,d}") print("csv must be read whole:", f"{os.path.getsize('out/trips.csv'):,d}", "bytes")

Run it and compare with this real output. Your bytes match exactly if your DuckDB version matches; a different version may encode slightly differently.

Three questions

Clear all three and analyst session 1 gets stamped in your passport.

1 · In S3, what is curated/nyc_taxi/?

S3 is a flat key space. The console draws folders from the slashes, but access, lifecycle, throughput and pruning all work on prefixes.

2 · Average tip by payment type reads 10,095,345 bytes from the CSV and 197,417 from the Parquet file. Why?

Both hold the same 100,000 trips. Column pruning plus compression is why a narrow question costs 1.96 percent of the CSV's bytes.

3 · On the sample, a whole-month query reads 3,023,334 bytes from the partitioned layout and 2,387,037 from one Parquet file. What does that teach?

The same mechanism that skips 30 folders for a one-day question adds 30 footers to a whole-month one. Partition on the filter you use, at a grain that keeps files large.
