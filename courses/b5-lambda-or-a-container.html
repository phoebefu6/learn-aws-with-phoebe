Part 1 · covers the event-driven handler

A file lands, a function wakes, a file leaves

5 min live

The handler does four things and nothing else. It reads the bucket and key out of the S3 event, downloads that object to /tmp, asks DuckDB to rewrite the CSV as Parquet, and uploads the result under curated/ with the same date in its name. On the 15 January slice of the sample, the build-along measured 262,544 bytes in and 81,729 bytes out: the curated copy is 31.1% of the raw one (derived from those two numbers). Everything interesting about the design is in what it refuses to do.

LiveEvent in, object out: the handler line by line3 min▶

The event is a pointer, not the data. event["Records"][0]["s3"] holds a bucket name and a key. The 262,544-byte file never travels inside the event; the handler fetches it. Scratch space is /tmp. The file is downloaded to /tmp/in.csv because that is the writable disk a Lambda function gets. DuckDB does the conversion in one statement. COPY (SELECT * FROM read_csv_auto(...)) TO '/tmp/out.parquet' (FORMAT parquet) infers the columns and writes Parquet; session 1 showed why the curated copy is the one worth querying. The output key is computed from the input key. raw/ becomes curated/ and .csv becomes .parquet, so raw/nyc_taxi/2024-01-15.csv always produces curated/nyc_taxi/2024-01-15.parquet.

The function returns a small dictionary with both keys and both sizes. That is not decoration: it is what you log, and what you check when someone asks whether yesterday's file made it.

Self-studyIdempotency: the same event should make the same file2 min▶

Design every handler as if the same event might arrive twice. These pages did not verify S3's event delivery guarantees, which is exactly why the professional norm is to make a second run harmless rather than to hope it never happens. This handler gets that almost for free: the output key is a pure function of the input key, so a second run overwrites curated/nyc_taxi/2024-01-15.parquet with the same content instead of creating a second copy. Compare a handler that names its output with a timestamp or a random id: run it twice and the curated zone holds the day twice, and every Athena query from session 4 double-counts. Homework 1 makes you prove the property on moto.

Self-study/tmp is scratch, not storage1 min▶

Lambda's /tmp can be set from 512 MB to 10,240 MB ("Lambda quotas"). Tonight's peak is both files at once, 344,273 bytes, a sliver of the smallest setting. Two habits keep it boring. Write to fixed names you overwrite, as this handler does, so a leftover file from an earlier run cannot be mistaken for this one; how long /tmp contents survive between invocations is not something these pages verified, so never rely on them being either there or gone. And anything that must outlive the invocation goes to S3, never to /tmp.

Real world

The function that kept feeding itself. A team wires a converter to "object created" on the whole bucket and writes its output back to the same bucket. Every output is an object created, so every output wakes the function again, and the invocation count climbs with nobody uploading anything. The fix is structural, not clever: inputs in raw/, outputs in curated/, and a trigger filtered to prefix raw/ and suffix .csv, so the function cannot hear its own writes. The scenario is constructed; the separation of zones is the one session 1 drew.

Part 2 · covers the Lambda quotas, and what a mock does not check

The box the function has to fit in

5 min live

Lambda is cheap and effortless right up to the edge of its quotas, and then it is not an option at all. The edges are published on one page of the developer guide, "Lambda quotas", and the build-along found the most important lesson about them by accident: moto accepted a 901-second timeout that real Lambda caps at 900. The mock ran the code; it did not check the box. You do.

LiveThe numbers that box a function in3 min▶

All from AWS's "Lambda quotas" page, read 3 October 2026; quotas change, so re-check before a design depends on one.

  • Timeout. "900 seconds (15 minutes)." No setting goes higher. A job that needs longer must be split into smaller pieces or run somewhere else.
  • Memory. "128 MB to 10,240 MB, in 1-MB increments." CPU comes with memory: "At 1,769 MB, a function has the equivalent of one vCPU."
  • /tmp. "Between 512 MB and 10,240 MB, in 1-MB increments."
  • Package. A zip of 50 MB zipped and 250 MB unzipped including layers, or a container image up to 10 GB.
  • Payload. 6 MB each way for a synchronous call, 1 MB for an asynchronous one (not the older 256 KB you may still see quoted), and 200 MB for a streamed response.
  • Concurrency. 1,000 concurrent executions by default, raisable; and "New AWS accounts have reduced concurrency and memory quotas".
LiveThe 901-second lesson2 min▶

Step 4 of the build-along registers a function called too-long with Timeout=901, one second over AWS's ceiling. moto 5.2.3 stored it and printed it back. Real Lambda would refuse that configuration. Nothing is wrong with moto: it is a mock of the API's shape, built so code can run without an account, not a reimplementation of every service's rules. Session 2 met the same edge from the other side, where moto's IAM enforcement was a teaching aid rather than AWS's evaluation engine. The working rule: a green run on a mock proves your code calls the API correctly. It proves nothing about quotas, limits or permissions. Check those against the documentation, in code if you can, and confirm on a real account before anything depends on them.

Self-studyMemory is also the CPU dial2 min▶

The modelled job runs at 1,024 MB, below the 1,769 MB point where the quota page says a function has one full vCPU. A CSV-to-Parquet conversion is CPU work, so more memory may finish the same file faster, and Lambda bills memory times time. Whether a faster run at more memory costs less, the same or more depends on how the job scales, and these pages did not measure that: the 0.04 s in tonight's output is a laptop, not Lambda, and timings vary by machine. Measure two or three memory settings on a real account and price each run with Part 3's formula before choosing.

Real world

The backfill that hit fifteen minutes. A daily handler like tonight's runs for months without a fault, one day's file at a time. Then someone needs a year reprocessed and drops the whole year into raw/ as one file. The function times out at 900 seconds, partway through, and writes nothing, because the upload is its last step. Nothing in the code changed; the input outgrew the box. The usual answers are to keep the unit of work small (one day per object, one object per invocation) or to run the backfill as a container job with no Lambda ceiling. The scenario is constructed; the 900-second limit is from "Lambda quotas". How to schedule and orchestrate backfills is taught in learn-data-orchestration.

Part 3 · covers the bill: Lambda against Fargate

Paying per run, or paying to stay on

5 min live

Lambda has two meters: $0.20 per 1 million requests, and $0.0000166667 per GB-second of memory times duration, billed to the nearest millisecond. A Fargate container has two different ones: $0.04048 per vCPU-hour and $0.004445 per GB-hour, for as long as it runs, whether or not a file arrives. (All us-east-1, AWS Price List, 3 October 2026; prices change, so re-verify before relying on them.) One prices work done; the other prices time available. The build-along turns both into monthly bills for workloads we chose, which are modelled; the prices are real.

LiveThree bills from the build-along3 min▶

The script prices one modelled job, 20 seconds at 1 GB per file, at two rates, and one container left running all month (730 hours):

  • One file a day. 30 runs, 600 GB-seconds: $0.01 a month on Lambda.
  • One file a minute. 43,200 runs, 864,000 GB-seconds: $14.41 a month. Almost all of it is duration; the requests come to under one cent.
  • A container always on, 1 vCPU and 2 GB. 730 x (1 x $0.04048 + 2 x $0.004445): $36.04 a month on Fargate, the same whether it handles one file or a hundred thousand.

All three at us-east-1 prices from the AWS Price List, 3 October 2026; re-verify before relying on them. The workloads are modelled: your job's duration and memory are what move these numbers, so your numbers will differ.

LiveWhere the lines cross2 min▶

One run of the modelled job costs 20 x 1 x $0.0000166667 + $0.0000002 = $0.000333534. Divide the container's $36.04 by that and the lines meet at about 108,000 runs a month, roughly two and a half a minute, around the clock. That figure is derived from the numbers above, not measured, and it moves with every input: halve the duration and the crossover doubles. Below it, paying per run wins; above it, paying to stay on wins, on the bill alone. The bill is not the only argument. A container has no 900-second ceiling from Lambda's quota page, which settles a 20-minute job before any price is compared. Fargate's own limits and how to run containers on ECS are outside these pages.

Self-studyWhat the free tier changes1 min▶

Lambda's pricing page says "The free tier includes one million requests and 400,000 GB-seconds per month." The script does not apply it. If your account has it, one file a day (600 GB-seconds) costs nothing at all. One file a minute uses 864,000 GB-seconds, so 464,000 are billed: about $7.73 a month, derived from the price per GB-second, with every request inside the free million. Because the free tier is a fixed monthly allowance, it shifts where the lines cross without changing how steeply Lambda's line climbs.

Real world

The every-minute poller. A team's daily conversion is so cheap it is invisible: about a cent a month. A stakeholder asks for fresher data, so the job is rescheduled to check every minute, still at about 20 seconds a run. The bill moves to $14.41, still well under a container that is always on, and nobody needs to change platform. The conversation that matters comes when volume heads toward the crossover, around 108,000 runs a month for this job, or when a single run approaches fifteen minutes. The scenario is constructed; the bills are the build-along's modelled workloads at real prices. If the real ask is continuous, sub-minute freshness, that is a streaming design, taught in learn-streaming-data.

★ Step 2 · b5_lambda.py, part 1# Analyst session 5 - Lambda or a container. The handler runs locally on moto S3; the bill uses real prices. import io, json, os, time, zipfile, boto3, duckdb from moto import mock_aws os.environ.setdefault("AWS_DEFAULT_REGION", "us-east-1") # us-east-1, AWS Price List, retrieved 2026-10-03 LAMBDA_REQ, LAMBDA_GBS = 0.20 / 1e6, 0.0000166667 FARGATE_VCPU_HR, FARGATE_GB_HR = 0.04048, 0.004445 def handler(event, context=None): """S3 put event -> read the CSV that landed -> write it back as Parquet under curated/.""" s3 = boto3.client("s3") rec = event["Records"][0]["s3"] bucket, key = rec["bucket"]["name"], rec["object"]["key"] s3.download_file(bucket, key, "/tmp/in.csv") duckdb.execute("COPY (SELECT * FROM read_csv_auto('/tmp/in.csv')) TO '/tmp/out.parquet' (FORMAT parquet)") out_key = key.replace("raw/", "curated/").replace(".csv", ".parquet") s3.upload_file("/tmp/out.parquet", bucket, out_key) return {"in": key, "out": out_key, "bytes_in": os.path.getsize("/tmp/in.csv"), "bytes_out": os.path.getsize("/tmp/out.parquet")}

Price three workloads. lambda_month is requests plus GB-seconds; fargate_month is vCPU-hours plus GB-hours for 730 hours. The workloads are modelled choices; change them to your own job's numbers.

★ Step 5 · b5_lambda.py, part 4def lambda_month(invocations, seconds, memory_mb): return invocations * LAMBDA_REQ + invocations * seconds * memory_mb / 1024 * LAMBDA_GBS def fargate_month(vcpu, gb, hours=730): return hours * (vcpu * FARGATE_VCPU_HR + gb * FARGATE_GB_HR) print("one file a day, 20 s at 1 GB: Lambda ${:,.2f}/month".format(lambda_month(30, 20, 1024))) print("one file a minute, 20 s at 1 GB: Lambda ${:,.2f}/month".format(lambda_month(43200, 20, 1024))) print("a container always on, 1 vCPU 2 GB: Fargate ${:,.2f}/month".format(fargate_month(1, 2)))

Check yourself

Three questions

Clear all three and analyst session 5 gets stamped in your passport.

1 · A nightly conversion takes 20 minutes per file. What happens if you deploy it unchanged as a Lambda function?

"Lambda quotas" sets the timeout at "900 seconds (15 minutes)" with no higher setting. Memory buys CPU, not time. A 1,200-second job is outside the box before any price is compared.

2 · The build-along registered a function with a 901-second timeout on moto and it succeeded. What does that tell you?

moto mocks the API's shape so code can run without an account. It does not enforce every quota. Check limits against the documentation and a real account, never against a green run on a mock.

3 · A job runs 20 seconds at 1 GB per file. When does a Fargate container that is always on (1 vCPU, 2 GB, $36.04 a month) become cheaper than Lambda on the bill alone?

One minute costs $14.41 on Lambda, still under $36.04. The lines cross at about 108,000 runs, derived from the two prices for this modelled job; a job longer than 900 seconds settles the question before the bill does.
